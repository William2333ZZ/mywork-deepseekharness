# CTO 和 CTO 需要的同事（2026-10-06）

用户：「你思考 CTO 的角色和他需要的员工」；接着：「你参考卡帕西这里的，你看看怎么做」（见第四节）；「你搜索 Gbarin 的工作来设计，另外我不一定用飞书」（见第四节之二）。

照前面定下的规矩，这份不从我们的设想出发：先读做过这份工作的人怎么写，再看哪些活能交给同事。原文提取在
docs/research/cto-2026-10/（Larson 15 篇；Vogels、Brockman、Fournier、Majors、Elliott-McCrea、两位创业公司 CTO；
Shopify、DORA、Anthropic、Pragmatic Engineer、Obie Fernandez），以及我们 10-05 的需求调研第七节
（docs/research/2026-10-05-user-needs.md，技术管理者那一组，证据偏弱）。

## 一、CTO 是什么角色

**没有标准定义。** Vogels（Amazon CTO，2007）开篇就说这一点，接着照 Tom Berray 分了四类：

| 类型 | 做什么 | 管不管工程部门 |
|---|---|---|
| 基础设施经理 | 机房、网络、应用开发维护、安全（CIO 管不过来的部分） | 管，常见于传统企业 |
| 技术远见者兼运营 | 决定技术怎么实现业务战略，再负责落地和运行；常是联合创始人 | 管 |
| 对外技术官 | 客户和研发之间的桥，跟关键客户、市场调研、产品组合 | 不直接管，靠影响 |
| 大思考者 | 技术能开出什么新业务、对手会怎么颠覆、前沿和原型 | 不直接管，带小团队孵化 |

几位一线 CTO 的说法互相补充：

- **先是高管，再是技术人。** Fournier：CTO 是「公司当前阶段需要的战略性技术高管」，不是技术阶梯的顶端，也不一定是最好的工程师。
- **多数 CTO 其实是「促成者」。** Brockman 在 Stripe 问了约 20 位 CTO 和 VPE，只有 1 位是首席架构师；到了 OpenAI，Brockman 的 CTO 工作就是写代码，把它当作了解组织的反馈回路。
- **能上能下。** Majors：向上对董事会讲到合适的抽象层次，向下能钻到细节里帮一个卡住的工程师。
- **人和技术分不开。** Elliott-McCrea（Etsy）认为「CTO 管技术、VPE 管人」的分法根本上是坏的。
- **小公司的 CTO 一半在动手。** Ojstersek（15 人公司）大约六成管理、四成亲手做（写规格、code review、性能、概念验证）。

所以「CTO 需要什么同事」先要问是哪一类、公司多大。Larson 给了按规模的分段：50 人以前流程由高管自己跑，50–200 人
人事和工程师分担，200 人以后才有专职的工程运营——**在这之前，那些活都落在 CTO 本人身上**，这正是同事能接的地方。

## 二、时间花在哪

把各位写到的事按节奏排（出处在括号里）：

| 节奏 | 事 |
|---|---|
| 每天 | 早上看本周重点、待办、今天的会（Obie Fernandez）；会后整理纪要、按人拆行动项（Obie）；守住写代码 / 想事情的时间块（Brockman、Ojstersek、Elliott-McCrea） |
| 每周 | 领导团队会、技术方案评审、事故复盘（Larson）；1:1 和跨级 1:1（Larson、Majors）；周五的 5-15 周报（Larson）；看指标，对比上月、上季、目标，每次变化先有假设（Larson）；招聘会（Larson） |
| 每月 | 工程 Q&A、经理月会（Larson）；按岗位看招聘四个数（Larson）；看 AI 用量：重度用户在做什么、不用的人为什么不用（Larson） |
| 每季 / 每年 | 工程指标季报（Larson 的模板：摘要 2–4 句、交付、约 3 张趋势图、编制、成本）；路线图；投入分配复审；年度预算；工程战略至少每年一改、发布两个月后复盘（Larson）；绩效校准每年两次（Larson） |
| 有事才做 | 写战略、做重大决定（Larson：诊断 → 政策 → 运营机制）；招关键岗位、说服候选人；事故；人员申请（Shopify：先证明 AI 做不到）；向上要解释 AI 投入（需求调研第七节） |

两条共同的体会：

- **时间不是自己的。** Fournier 转述的来信：一周没开始一半以上已被订满；Majors：一天切换上下文二十次；Ojstersek：「不管理自己的时间，别人会替你管理」。
- **该靠系统知道情况，不该靠打断人。** Fournier：先看看板、事故流程和复盘，再去问人；Brockman 最怕的「稀疏的微观管理」就是随机插手、推翻、然后消失。

## 三、哪些必须本人做，哪些是体力活

各家原文里明确留给 CTO 本人的，几乎一致：

- 战略的诊断和政策取舍、资源怎么分（Larson）
- 拍板和取舍、确认决策记录（Larson「决定而不是日期」；Obie 的决策日志写入前要本人确认）
- 对人的判断：高级岗位定级、非标薪酬、校准结论、关键候选人的说服（Larson）
- 选什么指标、定什么目标、怎么解释异常（Larson）；AI 立场、禁区、关掉没用的工具（DORA、Pragmatic Engineer 里的 Monzo）
- 难题当面答（Larson 的 Q&A）

明确能交出去的：

- 会议协调、议程、纪要、行动项（Larson：交给行政助理或项目经理；Obie：交给 Claude Code）
- 流程的日常运转：事故管理、组织规划、入职（Larson：200 人以后交给 TPM 或工程运营）
- 拉数、画图、填报告、统计招聘漏斗、维护 JD 库和面试流程文档（Larson）
- 定时检查、超阈值才提醒、例外审批的档案（Larson「运营机制」：这是最适合交出去的一类）
- 收集 AI 用法的成败案例和 prompt（Shopify、Larson、Anthropic）

还有两条约束，来自原文和我们自己的调研：

1. **定时、过滤、计数交给代码，模糊的判断才交给模型。** Larson 自己把安全告警的跟进做成 agent 之后发现：纯 agent 版本怎么强调也做不到「只发严重的」，而去打扰同事要求误报接近零；于是流程控制改成代码，只在「这事归谁」这种模糊处用 agent。这和我们「程序给事实、模型做判断」是同一条。
2. **发给别人的东西要 CTO 过目。** Larson 的误报要求、Obie 的「写入前确认」，加上需求调研第七节：管理者用 AI 写的东西会掉信任、下属一眼认得出。我们的规矩是能力不设限、做了告诉你，所以这里不加门槛，而是**建议 CTO 把「发给团队的消息」标成先问**（PROACTIVE.md 的用户可标先问）。

## 四、照 Karpathy 怎么做：一套组织库，一本账

用户 10-06：「你参考卡帕西这里的，你看看怎么做」。Karpathy 的做法（原文提取在 docs/research/cto-2026-10/karpathy.md）把上面五块收成两位：

1. **说过和定过的，进一套组织库。** Karpathy 的 LLM Wiki 里明写了团队用法：会议转录、聊天、项目文档喂进一套由模型维护的内部
   wiki，维护交给模型，所以它一直是新的。Obie Fernandez 的「Personal CTO OS」就是手搭的这个。所以 1:1、决定、项目、招聘的
   人和岗位、战略草稿、AI 的成败案例，都是**同一套库里的不同类别**，不是五位同事各记一本。
2. **数出来的，进一本账。** 交付、稳定性、成本、招聘漏斗、AI 用量这些数，由脚本算、记进一张表（像 autoresearch 的
   results.tsv），用户在一份 指标.md 里写看什么、目标、自己的判断（像 program.md）。Larson 2026 年的做法也是这样：定时、过滤、
   计数交给代码，模型只做模糊的判断。

| 同事 | 做法 | 用户做 | 它做 | 程序做 |
|---|---|---|---|---|
| **幕僚**（playbooks/cto-office） | Karpathy LLM Wiki 的团队用法；append-and-review 随手记；Software 3.0 的部分自主；Obie Fernandez 的晨报、会后同步、1:1 准备、决策日志；Larson 的 5-15 周报和「盯决定不盯日期」 | 开会、判断、拍板；往 随手记.md 最上面随手加 | 纪要和 1:1 一份一份收成 人 / 项目 / 决定 / 系统 / 招聘 / 综述 的页（先说要改什么再改，可整次撤销）；工作日 8:30 一页晨报；1:1 前只拿那个人的页和相关纪要；周五起草周报（个人感受留给你）；每周一体检；随手记只读、只建议哪几条该提上来 | `mywork_wiki_check`：孤立页、断链、没进索引，**到了重审日期的决定，过期和三天内到期的行动项**（`- [ ] 事（@人，截止 日期）`） |
| **工程体检**（playbooks/eng-health） | Larson 的度量和运营机制、用 agent 跑例行检查；DORA 2025；Pragmatic Engineer 的公司案例；Karpathy：数字结论附可运行的代码 | 在 指标.md 写看哪几个数、从哪拿、目标、自己的判断 | 写脚本拉数，记进 指标.tsv、画图；每周一只报违背判断或越过阈值的变化，每个数附命令；脚本失败一定说；值得记住的变化交给幕僚 | 脚本本身（每周按例行跑） |

几条 Karpathy 的做法直接变成了规矩：

- **一次一份、看着改。** Karpathy 自己收资料就是一次一份，先读摘要、看改动；幕僚收纪要先用 3–5 条说要改哪些页再改，「做了告诉你」那一行能整次撤销。
- **随手记是人的。** append-and-review 里「什么值得留在心上」是人决定的；幕僚只读 随手记.md，体检时建议哪几条该提上来，不改它。
- **上下文要挑，不要全塞。** 1:1 准备只拿那个人的页和相关纪要（context engineering）。
- **大判断找几路独立意见。** llm-council 的做法，默认不开：各自独立给结论、匿名互评、分歧列给用户；Karpathy 自己说模型互评的排名不等于对。
- **给图，不给大段字。** 工程体检的数配图，晨报不超过 15 行。

动手的那部分仍用已有的做法：代码研究、实验、评测、前沿、知识库。

## 四之二、照 GBrain 改幕僚（10-06）

用户：「你搜索 Gbarin（GBrain）的工作来设计，另外我不一定用飞书」。Garry Tan 的 GBrain（github.com/garrytan/gbrain，2026-04 开源，
他自己的库 15 万页、2.4 万人、5 千家公司；提取在 docs/research/cto-2026-10/gbrain-repo.md 和 gbrain-garry.md）是 Karpathy LLM Wiki
做成生产系统的样子。幕僚借了它这几条，没借的也写在下面：

| 借的 | GBrain 怎么做 | 幕僚怎么做 |
|---|---|---|
| 一页的格式 | 顶部 compiled truth（每次重写），`<!-- timeline -->` 下面只追加的时间线，每句带 `[Source: …]` | 同样两半；顶部写「更新：日期」「别名：」；时间线错了加「更正」，不改 |
| 会议回写 | 会议页不是产品，回写到每个人和公司的页才是；转写先归一成一条记录、拆多场、跨工具去重、认人靠证据、核对原话 | 收资料七步照这个写；会议软件的摘要只当「说法」，没出处的进「未核实」 |
| 冲突 | 新旧打架时旧的赢，报告给用户 | 旧的先不动，写进 wiki/待确认.md；晨报的「等你拍板」只从这一页来 |
| 先查库 | brain-first：先查库，查不到再找外面，找到写回 | 回答、备会、问用户之前先查库和日程 |
| 时间交给程序 | 日历先落成本地文件，时间用脚本算（他的 agent 曾把 88 分钟后的会算成 28 分钟） | 新工具 `mywork_calendar`：任何一家的日历订阅链接或 .ics 文件，镜像到 日程/日历.ics，代码算本地时间和还有几分钟 |
| 未了的事 | open loops「谁在等谁」靠状态关闭，不删 | `- [ ] 等 @人 什么（自 日期）`；程序列出等了一周以上的 |
| 夜里整理 | dream：去重、修引用、找矛盾、过时的结论；有护栏（不删、熔断、冷却） | 「每晚 22:00 整理」默认关；程序先查顶部比时间线旧的页、别名撞了的可能重复的页；不删，合并要用户点头 |
| 固化 | skillify：先手做 3–10 次，点头了再写成技能 | 同一类事第三次叫它做，问要不要变成例行或规矩 |
| 少开例行 | 定时任务出厂全关，一次开一个 | 默认只开晨报、周报、每周体检 |

没借的：给同事写「评价、动机」画像、去外面人肉搜索（GBrain 自己做团队库时会剥掉这些）；75 个技能、26 个夜间阶段、Postgres；
绑定 Google、Circleback、X 付费接口、靠 cookie 抓取。

**不绑定哪一家。** GBrain 原生只接 Google 和 Circleback，但它把来源做成可换的「配方」、日历先落成本地文件。幕僚同样不预设：
日历用 ICS（Google、Outlook、iCloud、飞书、钉钉大多能导出订阅链接），纪要用导出的文字、一个文件夹、转来的邮件或手记；要连账号、
要授权先问用户。10-06 的实测里幕僚去开飞书授权页，是因为我模拟回答时写了「日程用飞书日历」；playbook 里的飞书示例已经删掉。

## 五、不做的，和为什么

- **不做「盯模型和工具变化」的同事。** 用户 10-05 已经否掉（「完全没用」）；调研里事件是真的，需求是推断。
- **不做给 CTO 的每日 AI 资讯。** 需求调研第七节复核后是这一组里最弱的；想要的人用「前沿」。
- **不替 CTO 在团队里催人、问进度。** Fournier 和 Brockman 都把「频繁打断工程师问状态」「随机插手」列为失败方式；状态从看板、git、事故系统读。
- **不替 CTO 发向上、对外的定稿。** 掉信任；起草可以，判断那几句留给本人（Larson 的季报模板也是这样分的）。
- **绩效校准和薪酬只做算术。** Larson 列的体力活（评级分布、薪资带异常、合计是否超预算）可以做，但数据极敏感，只存本机，不进任何汇总。
- **同事也会只维护流程、不删流程。** Larson 说专职流程岗位有这个倾向；每位同事每月要问一次「这个还要不要」。

## 六、放进产品（已做）

- 两种新做法 playbooks/cto-office（幕僚）和 playbooks/eng-health（工程体检），和其余七种一样由 MyWork 生成；没有固定的同事、没有专用面板。
- MyWork 的规矩多了一条：用户只说了角色（「我是 CTO」），没说要哪种同事时，先看适合的做法、问一件最能决定配什么的事（团队多大、时间最多花在哪），再建议先配一两位，用户点头了再建。
- 要读的东西：日历、会议纪要、git / CI、事故系统、云账单、招聘表、聊天。同事有实时浏览器（用户已登录的 Chrome）和 MCP；要登录时请用户在浏览器里登录，或者导出文件丢进来。
- 人和薪酬相关的页只在本机，不交给别的同事。

## 七、证据强弱和缺口

- 最强：Larson（在职和前任 CTO，15 篇一手，含 2026 年的 agent 做法）；Obie Fernandez（在职 CTO 第一人称，但数字是自报、只有三周）。
- 一手但年代较早：Vogels（2007）、Brockman（2014、2017）、Fournier（2015）、Elliott-McCrea（2013–2025）。
- 调查和厂商：DORA 2025（近 5000 人）、Anthropic（厂商自述）、Pragmatic Engineer（18 家公司，部分付费没读到）；Shopify 是 CEO 不是 CTO。
- 没找到：Majors 专谈 CTO 职责的文章；**中国 CTO 本人的说法**（需求调研第七节同样缺）；任何一位 CTO 给出的「每周花多少小时在这些体力活上」的数字。
- 要访谈确认的：五位里哪一位最先付费；招聘和工程体检要接的系统，国内团队实际用的是哪些（飞书、钉钉、Jira、自建）。
