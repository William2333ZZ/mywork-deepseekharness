# 可靠性与运维审查：方案 A / B / C

路径缩写：
- `V2` = `/Volumes/KESU/deepseek_harness_projects/Mywork_deepseekharness-v2`
- `R` = `<scratch>/research`

证据边界：
- 大陆可达性全部是推断（`R/gaps.txt` 多处写明探测出口不在大陆）。
- 我只读了研究文件和 v2 代码，没有发任何网络请求。
- 标「常识」的是我自己的知识，不在研究文件里。

## 0. 三个方案都没解决的六件事

1. **没有热修通道，却把最易碎的东西钉死在安装包里。**
   - 三者都「锁 commit 和 sha256、不自动更新」，同时把财联社签名、金十请求头、巨潮 POST 的脚本和 stock-sdk 打进安装包。
   - `V2/apps/desktop/main.js` 没有 autoUpdater；`ensureHome()` 只在 profile 不存在时拷一次模板，之后升级不刷新。
   - 财联社签名「change without notice (the CLS `sv` version matters)」，旧 `/nodeapi/telegraphList` 已 404（`R/candidates.json`「中文财经快讯直连端点」）。
   - stock-sdk「v2 was a breaking rewrite; single maintainer」，2026-10-03 还在发版；a-stock-data 的更新日志记了 2026-09 端点死亡。
   - A、B 没有通道，C 有但排在 12 周。修一个签名要用户重装约 1 GB 的未签名安装包。
   - 交易日历文件按年命名（`cn-trading-2026.json`），年底到期，同样要靠这条通道。

2. **「准时」依赖一台醒着的电脑。**
   - `main.js` 没有 openAtLogin、powerSaveBlocker、托盘常驻。
   - 调度是进程内 30 秒 tick，错过的在启动时补跑一次（`V2/packages/tasks/src/index.js:947-948`）。
   - 补跑时所有到期例行同时入队，并发 2、单次 20 分钟（`index.js:36`），`routines.due()` 没有优先级和先后依赖。MyWork 的合并晨报可能先于各同事的补跑。
   - 只有 A（盘中不补跑）和 B（`staleAfterMinutes`）处理了过期，C 没有。

3. **手机这条路压在 workers.dev 上。**
   - 默认中继是 `https://mywork-relay.a313295747.workers.dev`（`V2/packages/kit/src/index.js:33`）。
   - 研究两处写明 workers.dev 在大陆不可靠（`R/patterns-ai-and-registries.txt` 的 ai-products PITFALLS；candidates 里 `duanyytop/agents-radar` 的风险）。
   - 这是 owner 的决定，不重议。但三个方案的引导都以「扫码配手机」收尾，没有一个把已有的 IM 推送（飞书、钉钉、微信，境内）设为晨报默认送达。
   - `relayUrl` / `MYWORK_RELAY_URL` 覆盖项已存在，可做应急切换。

4. **代理没有接线，「一手核对」在无代理时无法执行。**
   - Node 的 fetch 不读系统代理（常识）。三者都没写采集脚本、uv、npm 怎么拿到用户的代理，结果是浏览器能开 openai.com，探测脚本却判「海外不通」。
   - 「聚合站只能提名、必须有一手链接」在无代理机器上做不到，因为一手页正是不可达的那批。三者都没定义这时是标「未核对一手」照报，还是不报。
   - 探测只在首次做一次，没有写何时重探。

5. **评分、关键价位、仓位没有确定的计算来源。**
   - 这是三者共同的卖点，但没有一个写明由哪个脚本、哪个公式算。
   - 一条永久对话里留着昨天的报价，取数失败时模型最容易拿旧数当新数。
   - 台账「按收盘价机械结算」没处理除权除息和停牌（常识）；研究里 dsh-alpha-desk 的规则还有「dead zone」。
   - PDF 一律用 liteparse，其 README 自己说密集表格、多栏、扫描件效果差；研究列了跨页表、单位只在表头出现一次、合并与母公司报表重复等坑（`R/patterns-finance.txt` fin-docs §9）。

6. **锁文件管不到包外的 skill 和运行时拉取的代码。**
   - dsh 还会发现 `$DSH_HOME/skills` 和 `~/.agents/skills`（STRUCTURE.md 扩展点 1）。用户为别的 agent 跑过 `npx skills add`，那些 skill 对所有同事可见，不经过锁和扫描。
   - 扫描器不是保证：SkillSpector「a clean scan is not proof of safety」；snyk/agent-scan 要 token、把数据发给 Snyk、CLI 输出标为实验性。
   - 读正文的路径（论文、公告 PDF、Chrome 读页）把原文带进一个有 bash、有网络的会话，防注入只靠提示词。

## 方案 A

### (1) 最严重的问题

**A1. 没有脚本级的数字闸门。**
- A 的纪律都写在 duty.md 里；核验是「每个模板可带自己的核验提示」加借来的自检，都是模型核验。
- 研究结论相反：「VERIFICATION IS DONE BY SCRIPTS, NOT BY ASKING NICELY」（`R/patterns-finance.txt` fin-skills §6）。
- 引擎里 `verify: false` 是默认（`index.js:36`）。A 是三者里唯一给评分和价位却没有确定性校验的。

**A2. 默认信源里有已知陈旧或不存在的。**
- 「Olshansk/rss-feeds 补 Anthropic 和 Meta」：`feed_meta_ai.xml` 最新一条是 2026-07-27（candidates，Olshansk 条）。
- 「厂商 .md 更新日志（智谱、Kimi、MiniMax）」：Kimi 的 llms.txt 只有 hosted-agents changelog，没有模型更新日志（`R/gaps.txt:113`）。
- 模型表的 `LMArena名次` 列来自 HF，candidates 标 `cn: no`。表里只有行级「核对日期」，这一列会静默停在旧值。
- 价目没有覆盖 DeepSeek、阿里、火山、百度、腾讯（它们没有 .md，要读页面）。
- 「tidings-rss 的 AI 包」整包做默认：99 条里约 20 个低相关的个人博客，公众号和播客行指向同一批个人桥。

**A3. 健康检查太慢，修复靠用户的模型。**
- 体检在周一 09:00，备用地址也到那时才试；替换信源由同事「提议」。
- 私有签名端点没有备用地址可试。
- 信源表没有 `origin` 列，分不清包内行和用户行，无法远程修补默认行。
- 健康列和模型手改的列在同一张 16 列 CSV 里。采集脚本和模型写同一个文件，一次列错位就让全部采集失败。

**A4. 07:00 到 07:30 靠钟点做隐式依赖。**
- 夜班补漏 07:00、宏观 07:10、盘前 07:30，盘前要读前两者的表，而引擎没有先后依赖。
- 三季报截止 10-31（常识），首月最后一周晚间公告量是平时数倍。研究样本「4,747 条 / 09-29 到 10-04」还是国庆周。
- 夜班读 PDF 超过 20 分钟被取消，盘前读到的是旧公告库。

**A5. 供给和自己的规则矛盾。**
- A 规定包里不能有 dsh 插件，却把 dsh-jike（0 星、0.1.1、单作者）和 dsh-futu-mcp（0 星，refresh token 不超过 14 天要人工重登）列入供给。
- A 拒绝「下载并运行安装器」的 skill，却把 Agent-Reach 列入一键安装；其安装流程正是让 agent 抓取并执行 raw.githubusercontent 上的 install.md。
- 一键安装的 Python 依赖没有带哈希的锁。

**A6. 跨同事没有全局限速。**
- 间隔「写死在预设里」，但脚本在各同事自己的 shell 里跑。
- 东财同时被盯盘（快讯，每 10 分钟）、夜班（公告列表）、研报（reportapi）、宏观（数据中心）和 stock-sdk 底层打到。
- 研究：东财是最脆的依赖，push2 返回 502，有封 IP 记录（fin-data §5）。
- A 自己写了投研用户多在公司机器上。同一出口 IP 多人装，会一起被封。

### (2) 与 STRUCTURE.md 和 owner 决定的出入
- 下单类工具「按名字直接拒绝」加券商只读：owner 的规则是 `mywork_ask` 先问，A 比决定更严。按名字匹配也漏（长桥有 DCA、grid 工具）。
- 内核 13 项里 5 项「中」；#6 连接器代理在钉住的 dsh 上未验证（A 自己承认并给了退路）。
- 其余一致：品牌、两个安装包、表沿用现有前 6 列。

### (3) 必须保留
- 默认名册只靠 Node，Python 严格可选；巨潮单并发；公告口径窄（自选股加行业）。
- 第一位是通才加 `handoff`：不依赖尚不存在的同事的表，专门同事加入后让出。

- 哨兵：脚本先行，按规则（阈值、涨停、炸板）才叫醒模型；交易日历；盘中不补跑。

### 缺的监控和兜底
- 数字闸门；热修通道和 origin 列；维护者侧每日检查。
- 失败当次就试备用；全局按主机限速；代理接线。

workers.dev 中继。A 把「次日 07:30 手机上那一份」定为留人的钩子，验收也压在「按时收到」上，而这条链路等于「电脑醒着」加 workers.dev。

## 方案 B

### (1) 最严重的问题

**B1. 金融版把 Python 放进默认路径，还排在第 2 周。**
- 「后台同时装数据引擎（金融版默认装）」「uv 随包并跑通一个 Python 环境（a-stock-data）」。
- uv 的 Python 本体从 GitHub 下，C 称之为「大陆网络下最脆的一环」。
- a-stock-data 是「One self-contained SKILL.md (structured Markdown + inline Python)」，34 个源、87 个端点。它不是可调用的 CLI，是让 DeepSeek 读文档现写 Python，「不用改就能跑」不成立。
- 它依赖 mootdx，而通达信公共服务器 2026-09 已停 K 线（fin-cn §7）。
- 所有 Python skill 共用一个 `py/default` 环境（a-stock-data、akshare、MinerU、UZI、last30days），依赖冲突是时间问题。
- 失败只写脚注「数据引擎未就绪」，没有重试和诊断。

**B2. 默认路径上个人运营的桥和中心 feed 最多。**
- 头条用 AIHOT 两个接口加 aihot skill、ai-news-radar 三个文件、BestBlogs OPML。
- 圈内用 follow-builders（经 jsDelivr）、BestBlogs 的 X 与公众号 RSS（xgo.ing、wechat2rss.bestblogs.dev）、Wechat2RSS 公共源。
- BestBlogs：「feeds run on one person's infrastructure… heavy use by a shipped product could get blocked or overload it」，OPML 自 2026-07-08 未更新。
- Wechat2RSS：「up to 24 h delay」。同一事件晚一天再来一次，被当成新条目。
- ai-news-radar 是滚动 24 小时窗口；电脑关两天就丢两天，无法回补。
- AIHOT：单人运营，约 60 次每分钟每 IP，旧接口 2026-10-31 关停。
- jsDelivr 可达性未测，对分支引用有缓存（常识：约 12 小时），每日 feed 可能静默晚一天。
- B 自己说头条 6 周后才不依赖 AIHOT。

**B3. 采集器实际是 skill，不是内核。**
- 第 2 节把 `mw-collect` 列为内核，第 7 节说「先做成第一方 skill，零内核改动」。「按主机限速」只在单个同事进程内有效。
- 盯盘自己直连四个公告端点，公告同事也直连同一批，各自并发不超过 4。18:00 仪表盘与公告轮询重叠时可到 8，越过研究给的阈值（「cninfo bans IPs above ~4 concurrent requests」）。
- 同一条公告会在两位同事的交付里各出现一次。
- 盯盘还要从尚未上岗的「快讯」同事的库里取快讯。

**B4. 例行里「请用户接手」做不到。**
- B：「遇到验证码立刻停，请用户接手」。引擎的例行提示写死「例行运行时不要提问」（`V2/packages/tasks/src/routines.js:294`）。
- 登录过期只能写进覆盖脚注，再由例行之外的卡片提醒；B 没设计这一步。
- 价目每天用真实 Chrome 读五家国内厂商页面。覆盖是对的，但读页要模型在场，「没变化不叫醒模型」对它失效。

**B5. 密钥和运行时代码不受约束。**
- 「dsh 会清掉像凭据的环境变量，所以要写厂商配置文件」：明文 key 落在用户主目录，任何同事 shell 里的任何脚本都能读。
- `uvx akshare-one-mcp`、`mcp-remote` 在运行时拉最新版，不受 skills.lock 约束。
- 一键装 MediaCrawler 和 xiaohongshu-mcp：用用户账号登录抓取，风险是用户账号被平台限制。
- 随包第三方 skill 是三者最多（Wind 5 个、Anthropic 4 个、jwangkun 4 个、ai-berkshire 2 个、a-stock-data），每次上游变动都要重审。

**B6. 没有维护回路。**
- 没有更新通道，没有 origin 列，没有维护者侧检查。
- 体检是 MyWork 每周日 21:00 在用户机器上跑。

### (2) 与 STRUCTURE.md 和 owner 决定的出入
- 「同事可以给观点，但不下单：按名称拒绝」：同 A，比「先问」更严。
- Python 在金融版实际成了默认；STRUCTURE 的约束是「bundled Node; Python is optional」。
- 「会推翻方案的情况」里写了收成一个产品、模板降级为示例，这是有条件地重议两产品决定。
- 例行中找用户，与引擎现有规则冲突（见 B4）。

### (3) 必须保留
- 数字核验闸门：每个数字必须能在本次运行的原始文件里找到。这是三者里最好的防幻觉措施，应提前到第 2 周。
- `probes.json`（分国内、海外、镜像）和开场一句话说明。
- T0 到 T4 五档，以及「每条 T4 源都要满足没有它简报也完整」。
- 例行字段 `pre`、`window`、`staleAfterMinutes`、`cooldownMinutes`、`maxAlertsPerDay`；快讯「只有标红且命中关键词才出声」。

- 承认并发 2 和 20 分钟并错开时间；用 mcporter 让 MCP 不占工具表；用户自装 skill 先进隔离目录。
- 东财只用于研报、数据中心、公告分类，行情走腾讯和新浪。
- 「未验证的技术假设」清单本身。

### 缺的监控和兜底
- 热修通道和维护者侧每日检查。
- 内核级全局限速和共享缓存（ETag/304）；公告只由一位同事抓取。
- Python 的带哈希锁、按工具隔离环境、失败重试。
- 桥的自有镜像；例行之外的重新登录流程。

### 首月最可能出丑的单一依赖
uv 拉 Python 加 a-stock-data。它是第 2 周的交付项，金融版默认安装，上游当月还在死端点。

## 方案 C

### (1) 最严重的问题

**C1. 「连续失败 3 次自动停用」在弱网下自毁。**
- 快讯每 30 分钟一跑，断网 90 分钟（高铁、酒店认证页、代理关了一上午）就把全部信源停掉。
- GitHub 系主机本来就「intermittently unreachable」（candidates，GitHubTrendingRSS 条）。
- C 没有离线判别，也没有自动重试和复活。
- 首次探测把不通的行标「需代理」并跳过，没写何时重探。用户之后开了代理，这些行仍被跳过。

**C2. AI 版第一位在无代理机器上约等于 AIHOT 加三家媒体。**
- 快报的境内源只有 AIHOT、量子位、36氪、极客公园。OpenAI、DeepMind、Olshansk 需代理；HN Algolia 和 ai-news-radar 可达性未知。
- C 称 AIHOT 为「免 key 主信源」，却没有脱离它的里程碑（B 有）。
- AIHOT：单人运营，「Content decisions are server-side and opaque」，旧接口 2026-10-31 关停。

**C3. 第一位同事依赖不存在的同事。**
- 早报的 mate.json 写 `{"file":"公告库.csv","mirror":"finance.gonggao"}`，日历表同理。
- 第 5 节规定其余同事「待上岗」，不自动开。第一天镜像是空的，早报的「昨晚公告」「今日日历」没有来源。

**C4. 预检条件对高频源无效。**
- C 的规则是「没有新条目且信源正常时，直接记静默，不叫模型」。五家快讯永远有新条目。
- 于是快讯和早报的盘中检查每 30 分钟都叫醒模型，每位每天约 8 次，在一条永久对话里累积上下文，还占并发 2 的槽位。
- A 和 B 用的是规则触发（阈值、标红、关键词）。C 也没有过期不补跑的规则。

**C5. 分发方式和并存方式都有运维隐患。**
- 版本包发成公开 npm 包（`mywork-pack-finance`），里面是财联社签名和金十请求头脚本。
- 研究记录的平台执法正是冲着公开分发的抓取能力来的：B 站律师函在 2026-01 和 2026-07 关掉两个库（`R/patterns-ai-and-registries.txt` ai-social §1）。包被下架，更新通道就断。
- 「两个安装包共用一个数据目录」：`main.js` 没有 `requestSingleInstanceLock`，CDP 端口固定 9333，例行存储是整文件覆盖写（`V2/packages/tasks/src/store.js` 的 JsonList，无锁）。两个应用同时开会双重调度、互相覆盖。

**C6. 范围最大，排期最紧。**
- 采集器自评「大，超过 1 周」，却和包加载器、模板实例化、skill 清单、base 包、两位同事、双平台安装包一起放进 2 周。
- 连接器代办要内核自带 MCP 客户端。
- 更新通道、用量预算、观点自动结算排到 12 周。金融版前 12 周给评分和价位却不结算。
- 脚本核验只查「数字有出处」，一个来源标签就能满足，不对照本次运行的原始文件。

### (2) 与 STRUCTURE.md 和 owner 决定的出入
- 表头改成英文 snake_case（`source_id, tier, mode`、`code,name,market`）。现有 6 位同事的信源表和情报库是中文列，用户在手机上按表格看、靠对同事说话来改。A 和 B 都保留前 6 列，C 需要迁移。
- 自带 MCP 客户端、新包 `packages/sources`、更新通道，与「prefer small backend changes」张力最大。不动 dsh 这一点守住了。
- 「纯数据包」与「可在 pack.json 声明插件成员」自相矛盾（已推迟）。
- 下单走 `mywork_ask` 审批：三者里唯一与 owner 决定一致的。但示例预设是 `"allow": ["*"]` 加按名字审批，名字不匹配的交易工具会漏。

### (3) 必须保留
- 信源表（人和同事改）与信源状态表（只由采集器写）分开。
- `origin(pack|user)`，包更新只修补用户没改过的包内行。
- 采集器进内核：全局按主机限速，每源各自游标，成功才推进。
- 维护者每天在大陆网络对全部种子行跑 `--check`；`pack-lint` 试跑全部信源行；签名的更新通道（要提前）。
- 自带 CPython 压缩包；每包一个 venv；带哈希的 requirements.lock。
- `mywork_connect`：密钥只在宿主，按调用者查白名单，大结果落盘，URL 打码。
- deliver 之后先跑检查脚本的钩子。
- 其余同事「待上岗」、一键开，不一次全开。
- 验收：大陆干净机器、10 分钟、不要 Python 和数据 key；第三个包内核零改动。

### 缺的监控和兜底
- 离线判别加退避重试，替代自动停用；探测定期重跑。
- 规则触发的叫醒条件；过期不补跑。
- 单实例锁；第一位同事自给自足。
- AIHOT 之外的境内一手清单（国内厂商文档、公告页）。
- 对照本次运行原始文件的数字闸门。

### 首月最可能出丑的单一依赖
AIHOT。它是 AI 版第一位同事的主信源，无代理时几乎是唯一信源，10-31 的接口关停正落在首月。

## 4. 排序与合成

**排序（可靠性与运维）：C 第一，A 第二，B 第三。**
- C 是唯一有维护回路的：状态表分离、origin、更新通道、每日检查、Python 自带。它的缺陷多是可改的规则。
- A 的默认路径最保守，首月坏得最少；但没有闸门、没有修复通道，坏了修不了。
- B 的防幻觉和额度设计最好，但默认路径上易碎件最多，Python 默认装。

**跨方案首月最可能出事的单点**：财联社签名和东财端点，原因是没有热修通道。

**合成必须取**
- 取自 C：
  - 状态表分离和 origin。
  - 内核采集器。
  - CPython 自带、哈希锁、每包 venv。
  - `mywork_connect`。
  - 每日检查和 pack-lint。
  - 更新通道提前到第 2 周，至少能推信源行、站点脚本、交易日历、npm 工具版本。
- 取自 A：
  - Node-only 默认名册。
  - 通才第一位加 handoff。
  - 首次基线回补。
  - 规则触发的哨兵。
  - 巨潮单并发、窄公告口径。
  - 花费记录。
  - 「5 人连续 5 天按时」验收。
- 取自 B：
  - 对照本次运行原始文件的数字闸门（第 2 周）。
  - probes.json。
  - T0 到 T4 和「T4 可缺」规则。
  - `staleAfterMinutes`、冷却、日上限。
  - 额度提示与降层标注。
  - 连接器 `probe`。
  - 隔离目录。

**合成必须丢**
- B 的：
  - 首启默认装 Python、单一共享环境、第 2 周跑通 a-stock-data。
  - `uvx` 和 `npx` 运行时拉最新版。
  - MediaCrawler 和 xiaohongshu-mcp 一键装。
  - 把 key 写进厂商配置文件作为常规做法。
  - 例行中找用户。
- A 和 B 默认路径上的个人桥：wechat2rss.bestblogs.dev、xgo.ing、Wechat2RSS 公共源、jsDelivr 上的 follow-builders，降为用户自己加的行。hf-mirror 和 LMArena 不进默认列。
- A 的：
  - 周检才试备用。
  - 健康列混在信源表里。
  - Agent-Reach 一键装。
  - 未自行 fork 和审过的 0 星 dsh 插件。
- C 的：
  - 连续 3 次失败自动停用。
  - 首位同事镜像别人的表。
  - 「有新条目就叫模型」。
  - 公开 npm 分发站点脚本。
  - 两应用共用数据目录而无锁。
  - 英文表头。
- 三者共同的按名字放行或拒绝交易工具：改为显式白名单加 `mywork_ask`。

**三者都没有、合成要新增**
- 晨报默认走 IM，中继作第二通道。
- 开机自启加到点防休眠；或明说「开盖后补发」，并给补发排优先级（第一位同事先，合并晨报最后）。
- 代理设置传给采集器、uv、npm；每次运行带短超时重试海外行，不靠一次性探测。
- 评分与关键价位由脚本按固定公式算，模型只解释；结算处理除权和停牌。
- 模型不可用时出规则版清单。
- 晨报合并时各同事的早间简报静默，避免同一事件通知两次。
- 跨同事统一的事件键：公告 ID、arXiv 号、仓库加 tag、模型 slug、规范化 URL。
- 每位同事的 skill 白名单要能屏蔽 `~/.agents/skills` 等包外目录。

1. 有没有一条干净的大陆家宽线路和一台 Windows 机器，每天对默认信源跑检查？谁值守？财联社签名变了，承诺多久修好（当个交易日内）？
