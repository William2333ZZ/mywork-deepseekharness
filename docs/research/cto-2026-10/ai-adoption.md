# 工程领导者怎么推 AI 落地（五个一手来源，2026-10-06）

## 工程领导者如何推进 AI 落地：5 个一手来源（2025–2026）

说明：五个来源的原文都已读过。整份报告只引用了一句英文原话（在第 2 条），因为我遵守的版权规则是每份回复最多一句引文，比任务里"每个来源一句"更严。查不到的内容在各条里写明了。

### 1. Tobi Lütke：Shopify 关于"reflexive AI usage"的备忘录
- **出处**
  - 作者 Tobi Lütke，身份是 Shopify CEO，不是 CTO。
  - 标题 "Reflexive AI usage is now a baseline expectation at Shopify"，2025-04-07 发在 X 上。他说是因为备忘录快被泄露了才自己公开。
  - https://x.com/tobi/status/1909251946235437514 ，全文通过 fxtwitter API 读到。
  - 后续文章：Daniel Beauchamp，"Serious results, unserious methods"，2025-10-28，https://www.shopify.com/news/unserious-exploration
- **做了什么、设了什么期望**
  - 把"去试试 AI"从建议改成硬性要求，范围是所有人，包括他本人和高管团队。
  - 三条执行手段：
    - GSD 项目的原型阶段应以 AI 探索为主。
    - 绩效评审和同侪评审问卷里加入 AI 使用的问题。
    - 申请人头或资源之前，团队要先证明 AI 做不到。还要设想"如果自治 agent 已经是团队成员，这块会是什么样"。
  - 其他安排：
    - 月度业务评审和产品周期里专门留时间讨论 AI 集成。
    - Copilot、Cursor、Claude Code 等工具提前配好。
    - 在 Slack 频道里共享 prompt。
  - 他本人通过每周视频、播客、全员会反复讲 AI。
- **怎么衡量**
  - 备忘录本身没有量化指标。
  - 半年后的官方文章称：AI 代码编辑器已全员使用，有数千个 Cursor 席位，每个团队都能无限量使用顶级模型，内部原型平台 Quick 已有 5000 多个站点。
  - Pragmatic Engineer 的文章（见第 4 条）提到 Shopify 有一个 token 花费排行榜，并公开表扬花得多的人。
- **领导者本人必须判断的**：定基线；把 AI 写进绩效评审和人头审批。
- **体力活**：收集各团队的成败案例；整理 prompt；审核人头申请里"AI 为什么做不到"的论证。
- **风险**
  - 备忘录只提到两点：很多人一次 prompt 不理想就放弃；停滞不前就是慢性失败。没有讨论质量和安全问题。
  - 我没找到一手资料说明评审问卷的具体题目，也没找到人头审核实际是怎么执行的。
- **【推论】最需要的数字同事**
  - 一个"AI 采用证据台账"同事：每周扫一遍频道、PR 和工具用量，汇总成功和失败的案例。
  - 有人申请人头时，替他起草并反驳"AI 做不到"的理由。
  - 最少输入：团队名单、可读取的频道和仓库、一句话的期望。

### 2. Google DORA，《2025 State of AI-assisted Software Development》
- **出处**
  - Google Cloud DORA 团队（Nathen Harvey、Derek DeBellis 等），2025-09-23。
  - 完整 PDF：https://services.google.com/fh/files/misc/2025_state_of_ai_assisted_software_development.pdf
  - 发布公告：https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report
  - 能力目录：https://dora.dev/capabilities/
  - 单独的《AI Capabilities Model》报告要填表才能下载，我没读，用的是主报告里同名的那一章。
- **主要发现**
  - 样本：近 5000 人的调查（2025-06-13 至 07-21），加上 100 多小时的访谈材料。
  - 90% 的人在用 AI，超过 80% 自认效率提高，30% 很少或完全不信任 AI 写的代码。
  - 每天和 AI 交互的时间中位数约 2 小时。
  - AI 和交付吞吐量正相关，但仍然和交付不稳定正相关；和倦怠、摩擦没有可测的关系。
  - 核心结论原话："AI's primary role in software development is that of an amplifier"。
- **七项 AI 能力**
  - 清晰并传达到位的 AI 立场
  - 健康的数据生态
  - AI 能访问的内部数据
  - 扎实的版本控制
  - 小批量工作
  - 以用户为中心
  - 高质量的内部平台
- **给领导者的建议**
  - 把 AI 采用当作组织变革来做。
  - 培训重点从"鼓励使用"转到"引导、评估和验证 AI 的产出"。
  - 资助平台工程。
  - 做价值流映射：组一个一线跨职能小组，并且要有高管背书。
  - 把文档、决策记录、历史工单以结构化、安全的方式提供给 AI。
  - 奖励验证、委派和 agent 编排这类行为。
  - 个人效率不应该本身被当作目标。
- **领导者本人必须判断的**：AI 立场和允许使用的工具；投资方向；长期目标是创新、速度还是质量；设定现实的期望。
- **体力活**：收集价值流数据；诊断各团队属于哪种画像；整理上下文；盯住不稳定性指标。
- **风险**
  - 系统本来就弱的组织，问题会被放大。
  - 局部提效会被下游的混乱吞掉。
  - 访谈显示，产能提升在一些组织被转成了更高的产出要求。
  - 报告里的客座文章警告：只追产出会损害老带新的技能传承。
- **【推论】最需要的数字同事**
  - 一个"系统体检"同事：每周拉 CI、部署和事故数据，看吞吐和不稳定性。
  - 对照七项能力维护一张差距表。
  - 最少输入：CI 和事故系统的只读权限、团队清单、AI 政策原文。

### 3. Anthropic，"How Anthropic teams use Claude Code"
- **出处**
  - Anthropic 官方，无个人署名。博客发布于 2025-07-24（PDF 元数据显示生成于 2025-06-04）。
  - 博客：https://www.anthropic.com/news/how-anthropic-teams-use-claude-code
  - 23 页 PDF：https://www-cdn.anthropic.com/58284b19e702b49db9302d5b6f135ad8871e7658.pdf
  - 内容基于对内部重度用户的访谈。
- **各团队委派了什么**
  - **数据基础设施**：用截图诊断 K8s 故障；财务同事用纯文本写好流程交给它执行；每次会话结束让它总结并更新 Claude.md；多个实例并行跑。
  - **Claude Code 团队**：边缘功能打开自动接受，让它自己循环跑，拿回约八成完成的结果再人工接手；核心业务逻辑则同步盯着。Vim 模式约 70% 的代码是它自主写的。
  - **安全工程**：事故中追调用链，从手工 10–15 分钟降到约 5 分钟；审 Terraform 计划；整理 runbook。
  - **推理团队**：查 ML 概念的时间降了约 80%。
  - **数据科学**：不懂 TS 也做出了 5000 行的看板。做法是先存档，让它跑 30 分钟，结果要么接受要么从头再来。
  - **增长营销**（一个人的团队）：广告文案从 2 小时降到 15 分钟。
  - **法务**：做了一个分流电话的原型，把周报自动化。
- **对领导者的含义**
  - 组织团队内部演示会来传播用法。
  - Claude.md 写得越细越好。
  - 敏感数据通过 MCP 接入，以便控制权限。
  - 学会区分哪些任务可以放手异步跑，哪些需要同步监督。
- **领导者本人必须判断的**：任务怎么分级；核心逻辑的审查；结果接受还是重来；数据边界。
- **体力活**：收集上下文；写测试；写文档和 runbook；处理 PR 里格式类的评论。
- **风险**
  - RL 团队说一次就成功的比例只有约三分之一。
  - 修它的错往往不如直接重来。
  - 它默认倾向于复杂的方案，注释也常加在奇怪的位置。
  - 法务指出深度 MCP 集成有安全隐患。
  - 这是厂商自述，没有对照组数据。
- **【推论】最需要的数字同事**
  - 一个"委派记账加任务分级"同事：记录每次委派是成功、重来还是人工接手，每周总结哪类任务可以放手。
  - 顺手维护 Claude.md 和 runbook。
  - 最少输入：项目文件夹和 git 仓库，以及他对"核心 vs 边缘"的划分。

### 4. The Pragmatic Engineer（只用免费可读部分）
- **出处**
  - 主文：Gergely Orosz 与 Laura Tacho（DX 的 CTO），"How tech companies measure the impact of AI on software development"，2025-09-16，月度免费期。https://newsletter.pragmaticengineer.com/p/how-tech-companies-measure-the-impact-of-ai
  - 补充：Orosz 与 Elin Nilsson，"AI's impact on software engineers in 2026: key trends, Part 2"，2026-05-19。这篇标为付费，我只读了公开预览部分。https://newsletter.pragmaticengineer.com/p/ai-impact-on-software-engineers-part-2
- **怎么推广和衡量**
  - 覆盖 18 家公司。
  - 核心指标（PR 吞吐量、周期时间、变更失败率、开发者体验）配合 AI 指标（采用率、满意度、节省时间、花费）。
  - 按 AI 使用程度切片对比。
  - 数据来源有三种：系统数据、约每季度一次的调查、工作流结束后的即时采样。
- **公司案例**
  - Dropbox：90% 的工程师每周至少用一次 AI；常用者每周多合并 20% 的 PR，同时变更失败率下降。
  - 微软：统计"糟糕开发日"。
  - 建议采纳率、代码行数这类指标正在被淡化。
  - Monzo：
    - 做迁移类工作能省 40–60% 的工作量。
    - 自动 Copilot 代码审查给的建议不可用，改成需要时手动开启。
    - 涉及客户数据的系统和数仓禁止使用 AI。
- **领导者本人必须判断的**：选一组能互相制衡的指标；划出禁区；关掉无效的工具。
- **体力活**：拉数据、发调查、做切片、收集成败案例和 prompt。
- **风险**
  - 供应商只给自己方便测的替代指标，还会藏起遥测数据。
  - 做 A/B 对照不现实。
  - 编码以外的 AI 使用几乎没人测。
  - LeadDev 的调查中，60% 的领导者说缺乏清晰指标是最大挑战。
  - 2026 年预览里受访者报告：
    - 代码库质量在下滑，代码审查流于形式。
    - 管理层把 AI 带来的增益当成新基线。
    - 按 50%、80%、100% 的使用率定目标，造成浪费。
    - 一家万人以上的公司因生产事故回滚了部分 AI 工具。
    - 初级工程师 token 花得多，原本属于他们的成长机会被 AI 拿走。
- **【推论】最需要的数字同事**
  - 一个"成对指标加季度问卷"同事：每周拉 PR 吞吐量和变更失败率，按 AI 使用程度切片。
  - 每季度发一份短问卷并归纳评论，标出速度和质量背离的地方。
  - 最少输入：Git 和 CI 的只读凭据、团队名单、他选定的 2–4 个指标。

### 5. CTO 第一人称：Obie Fernandez
- **出处**
  - Obie Fernandez，自述是 ZAR 的全职 CTO，刚上任三周，管 10 名工程师。
  - "Building a Personal CTO Operating System with Claude Code"，2026-01-25。
  - https://obie.medium.com/building-a-personal-cto-operating-system-with-claude-code-b3fb9c4933c7 。原页面被 Cloudflare 拦截，全文是从他的 Medium RSS 里取到的。
  - 选它的原因：作者是在职 CTO，写的是自己每天怎么用 agent 运转组织，细到命令名和目录结构。
- **做法和频率**
  - 新建一个文件夹，让 Claude Code（Opus 4.5）在计划模式下采访他，然后自己搭一套 markdown 体系。
  - 始终开着会话，写文章时同时开着 9 个；长内容多用语音输入。
  - **每天早上** `/morning`：读本周重点、待办事项、当天日历。
  - **每天多次** `/meetsync`：拉取 48 小时内的 Gemini 会议纪要，建会议笔记，按人提取行动项，更新团队名册、招聘管道和架构文档。
  - **1:1 之前** `/prep`：读历次 1:1 记录和待办，准备谈话要点。
  - **做决策时** `/decide`：记录决策和备选方案，写入文件前必须由他确认。
  - 通过 MCP 发 Slack、建日历、看 Linear。
  - 全部内容存在私有 git 仓库里。
- **三周的自报数字**（让 Claude 统计的）：82 份会议笔记，1 月开了 47 场会，18 次 1:1，23 人的档案。
- **领导者本人必须判断的**：决策本身和取舍；确认决策记录；优先级；对人的评价。
- **体力活**：会议归档、行动项、1:1 准备、发消息、更新招聘管道。
- **风险**
  - 文章几乎没谈风险，数字是自报的，也没有对照。
  - 他自己说的局限：只能在终端里用，结果会滚出屏幕，离开电脑就联系不上。
  - （推论，原文未提）团队名册里存着同事的个人信息，有隐私风险。
- **【推论】最需要的数字同事**
  - 这几乎就是目标形态：一个文件夹，加上定时晨报、会议同步、决策日志，以及写入前先问他。
  - 最少输入：一个空文件夹、日历和会议纪要的读取权限、一句"我的角色和本周重点"。
