## 1. Hamel Husain《Your AI Product Needs Evals》
- **作者和日期**：Hamel Husain，2024-03-29。案例是 Rechat 的房产助手 Lucy。
- **工作流**：分三级。
  - L1 是断言单元测试，每次改代码都跑。按"功能 × 场景"拆分，例如找房源分 1 条、多条、0 条三种情况，各写一个 len 断言；另有通用断言，例如用正则检查回答里没有 UUID。用 LLM 一次生成 50 条测试输入。测试放在 CI 里跑，结果连同 prompt 和测试版本存到 CI 之外，用 Metabase 看趋势。通过率不要求 100%，定多少是产品决策。
  - L2 是人工加模型评估，按固定节奏做。先记录 trace（用 LangSmith）。自己做查看和标注工具，用 Shiny 等不到一天就能做出来。一屏显示 feature/scenario、是合成还是真实输入、筛选、CRM 链接；输出可以直接修改，用来整理微调数据。标注只分 good/bad。起步时把所有测试用例和用户 trace 都读一遍，之后改为抽样，读到学不到新东西为止。
  - L3 是 A/B 测试，只在产品有重大改动之后做。
- **judge 怎么对齐**：每隔几天给专家 Phillip 发一张表，每批 25–50 条。列包括 model response、model critique、model outcome，再加 phillip_ 前缀的三列：他的 critique、outcome、期望回答。作者据此修改 judge 的 prompt。
- **人和 LLM 的分工**：人负责标注、写评语、定通过率。LLM 负责生成输入、帮忙想断言、写评语；评语用能负担得起的最强模型。
- **指标**：这个例子里约一半是失败，所以用了一致率；类别不平衡时应分开看 precision 和 recall。
- **限制**：对齐之后还要定期复查一致率；"正确"本身有主观性。
- **原话**："You are doing it wrong if you aren't looking at lots of data."
- **【推论】数字同事最少需要**：一个存 trace 的文件夹；断言脚本加定时运行，产出趋势表；能批量生成输入；能把表格发给用户填写再读回来。**必须留给人的**：good/bad 判定、评语、通过率阈值，以及决定什么时候可以信 judge。

## 2. Hamel Husain《A Field Guide to Rapidly Improving AI Products》
- **作者和日期**：Hamel Husain，2025-03-24。
- **错误分析（自下而上）**：表格里一行是一段对话，对任何不好的行为写开放式备注。然后用 LLM 从备注里归纳出失败分类，把每一行映射到分类标签，再用透视表计数。
  - NurtureBoss 的例子：标注了几十段对话后，发现日期处理有 66% 失败；三类问题（对话流、该转人工没转、改期/日期）占了 60% 以上。之后针对性写测试并量化，日期处理成功率从 33% 提到 95%。
- **数据查看器的要求**：所有上下文在一屏里；对/错一键标注；能写开放备注；能按渠道、物业等筛选排序；有快捷键。用 AI 辅助几个小时就能做出来；刚起步用电子表格也行。
- **合成数据**：按 features、scenarios、personas 三个维度生成。只生成用户输入，不生成回答。要接入真实约束，例如真实的房源 ID 和日程。还要核实生成的查询确实触发了目标场景，例如"无结果"的查询真的返回 0 条。
- **维持对评估的信任**：
  - 标准会漂移（criteria drift）。
  - 采用二元 pass/fail 加详细评语。评语放进 judge 的 few-shot 示例，作者称一致率通常因此高 15–20%。
  - Honeycomb 迭代三轮达到 90% 以上的一致率。
  - 规模变大时：早期由专家评大比例样本，研究人和模型在哪里分歧，把抽样集中在对齐最弱的地方，并持续定期校准。
- **人做什么**：让领域专家在产品的 admin 模式里直接改 prompt。
- **节奏**：路线图按"跑了多少实验"算，而不是按"上线了多少功能"。文中引 Eugene Yan 的做法：每两周汇报一次，每周写一份 fifteen-five。
- **失败方式**：用 helpfulness 这类通用指标的仪表盘制造虚假进步；指标太多导致注意力分散；团队不再信任评估，回到凭感觉决策。
- **【推论】**：数字同事可以承担归纳分类、计数、生成并核验合成数据。**必须留给人的**：写开放式备注、判断对错、确认分类是否合理。

## 3. Hamel Husain《Using LLM-as-a-Judge For Evaluation: A Complete Guide》（他称这套方法为 Critique Shadowing）
- **作者和日期**：Hamel Husain，2024-10-29 首发。
- **七步流程**：
  1. 找一位主领域专家。独立开发者可以自己当，但要诚实评估自己的专业程度。
  2. 建数据集：按 feature/scenario/persona 维度，用真实数据加合成数据；LLM 只生成用户输入。生成表里有一列"Assumptions"，写系统里预设的条件，例如"该订单号不存在"。把输入跑过系统后存成表：输入、回答、元数据。
  3. 专家给出 pass/fail 加评语，评语要详细到新员工能看懂、能直接当 few-shot 示例。一屏提供用户元数据、系统状态、可查询的数据库。从约 30 条开始，一直标到不再出现新的失败模式。
  4. 先修明显的错误，然后回到第 3 步。
  5. 建 judge：prompt 里放专家的示例（nlq/query/critique+outcome 格式），要求模型先写评语再给判定。把表（NLQ、生成的查询、critique、outcome）发给专家，专家填自己的版本；跟踪一致率，三轮达到 90% 以上。作者手工改 prompt，觉得 DSPy 效果不好。
  6. 错误分析：只在 judge 没见过的数据上，按维度算失败率（例：订单追踪 / 无结果 / 新用户 这一格是 75%）。在表格里手工给失败 trace 归根因，统计分布，"15 分钟就能走很远"。每修一个错误都补一个测试（断言或专门的 judge）。
  7. 需要时再建专门的 judge；能用代码断言的就不用 judge。
- **怎么验证 judge**：把它当二分类器看。专家标注的数据拆成三份：train 占 10–20%，只用作 few-shot；dev 占 40–45%，用来迭代 prompt；test 占 40–45%，冻结 prompt 后只跑一次。每份里 Pass 和 Fail 各要 30–50 例；每个失败模式约 100 例，少于 60 例时置信区间太宽。指标用 TPR 和 TNR：如果错误率只有 5%，judge 全判 Pass 也能有 95% 的一致率。
- **频率**：定期复查，有重大变化（例如换模型）时重做。前两轮之后侧重去找错误，但始终保留一部分随机抽样。
- **失败方式**：AI 的范围太大；没用主专家，或评语太简短；对一致率的期望不现实。judge prompt 常见的问题是：没有评语、评语太短、缺外部上下文、示例不够多样。作者认为 judge 的主要价值在于逼人去看数据。
- **【推论】**：数字同事需要能管理 train/dev/test 三份文件、跑 judge、算 TPR/TNR、在模型或 prompt 变化时自动发起复审。**必须留给人的**：pass/fail 和评语、根因分类是否确认。

## 4. Shankar 等《Who Validates the Validators?》（arXiv 2404.12272）
- **作者和日期**：Shreya Shankar、J.D. Zamfirescu-Pereira、Björn Hartmann、Aditya Parameswaran、Ian Arawjo。2024-04-18 提交 arXiv，后来收录于 UIST 2024。
- **EvalGen 工作流**（做在 ChainForge 里）：
  - 入口三选一：Infer、Manual、Grade First（选 Grade First 要先评至少 5 条）。
  - GPT-4 根据被测 prompt 提出二元评判标准；用户增删改，并为每条选用代码还是 LLM 来实现。
  - 另一个 LLM 为每条标准生成多个候选断言（Python 函数或 grader prompt），立即在全部输出上执行，淘汰报错的。
  - 等待期间用户对输出整体点 Good/Bad（不按单条标准），之前的打分可以回改。
  - 系统按"高低交替"抽样给人评；随机抽样的方差很大。
  - 每条标准选出与用户打分最一致的候选，可以设误判失败率阈值。
  - 最后出一张 Report Card：每条标准的混淆矩阵，加整体的 coverage 和 FFR。再在全部输出上跑一遍，表格的行是输出、列是断言。
- **指标**：
  - coverage：用户判坏的输出里，被断言判失败的比例。
  - FFR（误判失败率）：用户判好的输出里，被断言误判失败的比例。
  - alignment：coverage 与 (1−FFR) 的调和平均。
  - 离线实验只给了 16 条打分：产品任务上 EvalGen 的 coverage 是 0.73，全自动基线 SPADE 是 0.49；断言数 4 对 9。
- **用户研究（9 人）**：一般评 5–10 条，或评 10 分钟左右。有人建议应强制先看至少 20 条。
- **失败方式和限制**：
  - 标准漂移：看到新类型的坏输出就会加标准；已有标准也会被重新解释，例如"全部是专有名词"改成"大多数是"。
  - 有人为了和之前的打分保持一致，故意打低分。
  - 字数这类标准，人很难判。
  - 从自然语言转成代码时，LLM 的理解和用户不一样，用户评再多也纠正不过来。
  - LLM 断言更难让人信任；上线后怎么维护没有答案。
  - 研究本身的局限：只有两条流水线，9 名资深开发者，没有覆盖部署阶段。
  - 参与者提出想要每日邮件报告，以及把断言导出成单元测试。
- **Shreya 的博客《Data Flywheels for LLM Applications》（2024-07-01）**：每个指标定期从生产数据抽样标注，存进带时间戳的数据库；代码实现的指标要定期人工复查；可以让 LLM agent 定期提议增删改指标，但新指标集要由工程师核实。
- **【推论】**：数字同事可以出标准草稿、写候选断言、自动执行和挑选、发每日报告。**必须留给人的**：对输出打分、确认标准的定义和改动。

## 5a. Eugene Yan《Task-Specific LLM Evals that Do & Don't Work》
- **作者和日期**：Eugene Yan，2024-03-31。这篇讲"选什么指标"，不是完整流程。
- **按任务的做法**：
  - 分类/抽取：至少要分开看 recall 和 precision（准确率太粗）。有概率输出时看 ROC-AUC、PR-AUC，并画两类预测概率的分布；如果大量样本落在 0.4–0.6，就很难定阈值。
  - 摘要：基本不用测流畅度和连贯性。事实一致性用 NLI 模型判断：把原文当前提、摘要当假设，取"矛盾"的概率。几百条任务样本开始有用，上千条可以当护栏；可用开源的 FIB/USB 数据冷启动，ROC-AUC 从 0.56 提到 0.85。相关性用人工判断来微调。
  - 翻译：用 chrF、BLEURT、COMET、COMETKiwi，不用 BLEU。
  - 版权：用 HELM 的最长公共子序列和编辑距离；测试时取书的中段，不要用开头。
  - 毒性：用 RealToxicityPrompts 和 BOLD。
- **人做什么**：复杂任务仍以人工为准。用主动学习挑样本：高概率预测的去查假阳性，低概率的去查假阴性，0.4–0.6 的补标签。评估门槛按风险定（内部还是对外、是否允许自由输入）。事实不一致率常见在 5–10%，压到 2% 以下可能极难。
- **不管用的**：ROUGE、BERTScore 这类指标对好坏样本区分度太差；G-Eval 召回低、成本高；QA 类评估太复杂。
- **产物**：一张带 label 和 pred_proba 两列的表，加 4 张诊断图（文中附代码）。
- **【推论】**：数字同事需要能跑 sklearn/NLI 和画图。**必须留给人的**：金标准标签和风险门槛。

## 5b. Eugene Yan《Evaluating the Effectiveness of LLM-Evaluators》
- **作者和日期**：Eugene Yan，2024-08-18，综述二十多篇论文。
- **作者自己的决策顺序**：
  - 先定比较的基线。对人工：LLM 与人的相关要达到人与人的水平。对微调分类器：要达到同等的 precision/recall，这更难。
  - 客观任务用直接打分，主观任务用两两比较。
  - 能简化成二元就二元，用 recall/precision 或 Cohen κ；Likert 量表用 Spearman/Kendall。作者对相关性指标持怀疑。
  - 一个 prompt 只评一个维度，通常效果更好。
  - 开发阶段评几百条，用 API 加思维链加 n-shot 示例；生产护栏要低延迟，就微调分类器，用开源数据和内部 eval 的标签冷启动。
- **对齐方法**：介绍了 EvalLM（标准越具体，和人越一致）和 EvalGen。
- **限制**：
  - judge 有位置偏差、偏爱长回答、偏爱自己生成的答案。
  - 和非专家的相关性高于和专家的相关性，所以报告的数字可能虚高。
  - 一项研究里，GPT-4 的 κ 是 0.84，低于人与人之间的 0.97；简单的"包含子串"基线胜过一半的 judge。
  - 微调过的 judge 换一种评分方式就性能崩溃。
- **【推论】**：数字同事需要能算 κ 和 recall、能做位置互换测试。**必须留给人的**：专家标签。
