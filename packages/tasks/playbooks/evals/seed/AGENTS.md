# 评测的规矩

照 Hamel Husain、Shreya Shankar、Eugene Yan 写过的做法。判对错永远是人的事；同事负责其余的。

## 这个系统

（开工时写：做什么、谁在用、最担心哪类错、数据在哪、谁来判。）

## 文件

- traces/：用户给的原始数据（日志、对话导出），只读。
- 标注/YYYY-MM-DD.csv：一批要判的数据，列：编号,输入,输出,上下文,判定,备注。判定只写 pass 或 fail，备注写为什么（详细到新人看得懂，以后当 judge 的示例）。
- 错误分析/YYYY-MM-DD.md：失败类别、每类多少条、占比、最该先修的两三类。
- 测试/：代码断言和 LLM judge（每个一个文件），测试/通过率.tsv 记每次跑的结果。

## 看数据

1. 起步时让用户多看：30 条起，看到学不到新东西为止。之后每周抽样，随机的为主，再补几条可能出错的。
2. 用户在对话里说「3 fail：日期算错」就替他填进表里；丢回改好的表格也行。
3. 标准会漂移：用户看着看着改了口径，就把新口径写进本文件，并说清以前判过的哪些要重看。

## 错误分析

1. 先开放地从备注归纳失败类别（不先定框框），再给每条 fail 贴一个类别。
2. 出透视表：每类多少条、占 fail 的多少；按维度（功能、场景、用户类型）看失败率。
3. 每修一类错，补一个测试（能用代码断言就用断言）。

## LLM judge

- 能用代码断言判的不用 judge。一个 judge 只判一个维度，先写评语再给 pass/fail。
- 用户判过的数据分三份：train（10–20%，只当 few-shot 示例）、dev（迭代 judge 的 prompt）、test（冻结 prompt 后只跑一次）。每份 pass 和 fail 各要 30–50 条。
- 报 TPR 和 TNR，不只报一致率（失败只占 5% 时，全判 pass 也有 95% 一致率）。注意位置偏差、偏爱长回答。
- 换模型、改 prompt、数据分布变了，就重跑 test。
