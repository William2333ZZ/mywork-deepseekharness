# MyWork v2 · 手机端

> 一句话：**手机端和网页同源，不同形。** 会话当主屏，交付物是卡，条目页原样，动作只在条目页。第一版住在飞书里，App 等三件基础设施（客户端认证、服务端推送、外网可达）到位再换壳。

配合 [FLOW.md](FLOW.md)（正常的一天，其中「手机上：看通知、读结果、点个『有用』、说一句 — 同一套页面，单列」）、[../MYWORK-V2.md](../MYWORK-V2.md)、[../ECOSYSTEM.md](../ECOSYSTEM.md)（形态矩阵、顺序第 2 步「IM 反向」）读。日期：2026-09-30。

## 0. 结论

对「App 端就是 Cue 那种 UI，功能和 web 一样」的判定：

1. **骨架对。** 会话是主屏、交付物是流里可点开的卡、没有底部 tab、动作只在条目页。这是 Cue、Grok、Cowork、Kimi 的手机端共同收敛出来的形态，不是 Cue 独有；Cue 官方口径也是「同一套能力，布局按端调整」。
2. **「Cue 那种」的两个标志不要。** 多 agent 群聊（每条 agent 消息带头像、按 agent 淡色气泡）违反「用户气泡在右、回复是正文、无头像」；Agent 身份（邮箱 / 电话 / 钱包 / 电脑）不是网页功能，与四个对象无关，且上线两天、无用户证据、治理与信任数据偏负面（Gartner「自主性跑在治理前面」；仅 23% 消费者信任 AI 付款）。
3. **「功能和 web 一样」改成「同源」。** 数据层一样：同一套 `/mywork-tasks/api`、同一条今日线程、同一套引擎，网页每个用户动作都有 JSON 路由。页面层是子集：去掉原始对话、导出 PDF、IM 发送卡、机器配置；多出推送、听写、分享、配对。通知层完全不同：网页是轮询 + toast，手机必须是系统推送。
4. **今天拦路的不是 UI。** dsh 只在 `GET /` 用 `?token=` 换 HttpOnly SameSite=Strict、绑定 host:port 的 cookie，不收 Authorization 头，Origin 必须等于 Host；`mywork/task` 只是进程内 cordis 事件，没有 SSE / WebSocket / APNs / FCM；服务只在用户电脑 loopback。独立 App 今天连登录都做不到。
5. **顺序：飞书会话 + 同源 PWA 先行，Cue 骨架 App 后置、按触发条件做。** 条目页（任务页、例行条目页、任务列表、新任务）三种形态共用，不返工。
6. **不砍列表管理和过程。** 「手机上很少管列表、看过程」没有数据支持，头部产品反而把定时任务管理和进度查看搬上了手机。手机保留例行列表（暂停 / 恢复）、任务列表（筛选 / 搜索）、在跑行的当前步骤与耗时、任务页的过程折叠行和取消，只是不放首屏。

## 1. 形态与顺序

```
M0  飞书里的 MyWork 会话（借 dsh-im-connect）+ 桌面二维码 → 手机浏览器同源 PWA     2 周
M1  推送升级为交付卡、简报卡、清单关键词；设置 → 通知 → 飞书；侧栏手机分支打磨     3–4 周
M2  独立 App：Cue 骨架换壳，条目页不动；前提是配对 token、事件流 + 推送、外网可达   8–12 周，条件触发
```

M2 的触发条件（任一成立即开工）：交付物不再是能读的文字（交易工作台看板、图表、多表格报告）；任务过几百条、十条一页的「找 X」不够；多人 / 每人自己的今日；微信成主渠道而模型转发不可靠或平台政策收紧；需要在手机上排查过程；MyWork 上云、不再跑在用户电脑上。

**流的纪律**（S1、飞书会话、将来任何会话形态都适用）：

- 同一任务在流里最多两条：交办行原地更新进度，完成时新发一张交付物卡。进度只原地更新，不另发。
- 不发「开始了」。「进度」只答不推（说「进度」回一行一个在跑任务：标题 · 当前步骤 · 耗时）。
- 例行无变化绝不发；日报 / 周报 / 月报永远发；quiet 项只进第二天简报的折叠行。
- 卡是导航不是操作：交付物卡不放摘要正文、不放按钮（[看全文] 除外）。
- 单成员时没有会话列表：首页直接是 MyWork 会话。领域包成员出现后才有列表，且 MyWork 会话永远是默认入口、能建任何领域的任务；领域会话只是「该领域的例行和结果落在这里」（[../ECOSYSTEM.md](../ECOSYSTEM.md) §1「不让用户先选场景」）。三个月仍只有一个成员，列表不做。

**一处规则张力，需要你拍板**：提醒卡上的「知道了」、失败卡上的「再来一次」、等你看 sheet 行上的同两个按钮，与「列表上不放操作」相抵。网页今日清单今天就有这两个行内动作（MYWORK-V2.md「顺序：提醒（知道了）、失败（再来一次）」），手机沿用。若严格执行规则，把它们挪到例行页 / 任务页 ···，提醒从 1 步变 3 步（今日 → 条目页 → 按钮 → 返回），而这两个恰是手机上最高频的动作。建议：把「今日清单及其手机对应物（等你看、提醒卡、失败卡）每行至多一个按钮」写成规则的唯一例外，其余列表严格无操作。

## 4. 不做的事

来自 Cue、不是网页功能：
- Agent 身份：邮箱 / 电话 / 钱包 / 电脑（含「资产」区、三屏引导、远程桌面）。
- 群聊、多 agent 彩色气泡与头像、agent 之间 @。
- 扫码创建 Agent、「创建 Agent」、「看大家怎么用」、顶部一排 Agent 头像。
- 输入框的「+」附件（没有上传 API）和麦克风按钮（系统键盘自带听写）。
- 会话内的「电脑」图标（我们没有电脑面板）。

网页有、手机不做（都是「电脑这台机器」的事）：
- 「原始对话」（打开的是 dsh 会话的 Codex 页）。
- 导出 PDF（window.open + print，移动端拦弹窗）。
- IM 助理页的发送卡片。
- 模型 / API key、成员安装卸载、MCP、插件市场。
- 过程时间线里每次调用的原始参数 tooltip。
- 交付物按领域筛的独立页面。

形态上不做：
- 底部 tab 栏（M2 App）；M0 的 PWA 三 tab 是脚手架，M2 拆。
- 单成员时的会话列表。
- 第二种应用内通知面（toast 与卡片二选一：App 里只有卡 + 角标 + 系统推送）。
- 未读分割线、推荐模板卡、空态说明小字。
- 第二条飞书长连接（见 §6）。

## 5. 里程碑

### M0 · 两周 · 「飞书里说一句话就是任务，手机上能读结果」

1. **飞书会话**（借 `@michengai/dsh-im-connect`，不写入站代码）：在 IM 助理里把飞书账号的 agentPreset 设为 `mywork-assistant`（`packages/tasks/presets/mywork-assistant`，只有 mywork_task_create / mywork_routine_create），飞书私聊立刻具备三分法。tasks 包补三个小工具 `mywork_rate` / `mywork_ack` / `mywork_say`，让「有用」「知道了」「再短一点」落到 POST /rate、/routines/ack、/say 对应的 api。用 packages/im 已有的 session/event 监听 + chats.js 的 sessions.json 映射，把 IM 会话里的用户话与回复镜像到当天的 assistant 线程，网页今日能看到手机上说的话。只认 owner open_id；群聊和他人忽略。
2. **推送升级**：`packages/im/src/index.js:77` 从「summary 或第一份交付物标题」改为交付卡字段（标题 · 核验结论 · 领域 · 摘要 ≤3 行），`feishu.js` 直推路径加 `msg_type interactive`；文案末尾加「打开 MyWork 看结果」。
3. **网页新增一屏「设置 → 通知 → 飞书」**：绑定状态、五个开关（完成 / 失败 / 提醒 / 例行有变化 / 简报时间）、默认目标（`notifyConfig.automation.default`，今天没有 UI，`notify.js:10-13`）。
4. **同源 PWA**：桌面「设置 → 手机」一键以 `--host <局域网IP> --trusted-host <IP:port>` 启动并生成 10 分钟有效的 `?token=` 二维码（可吊销）；手机浏览器扫码换 cookie，manifest + M 图标 + standalone。`codex-ui/MyworkSidebar.tsx` 加 <720 分支变底部三 tab；补 visualViewport 软键盘处理、断连回连接屏。
5. 不做：简报卡、清单关键词、飞书云文档、微信、系统推送、Cue 骨架。

验收（一台真机，全程不开电脑网页）：飞书说「每 30 分钟盯一下 X 的价格，有变化告诉我」→ 收到「已安排」→ 有变化收到交付卡 → 点看全文（PWA 任务页）→ 点有用 → 飞书引用回复「只看 A 家」→ 收到新交付卡 → 回到电脑，网页今日下半部分有这段对话和交办行，任务页有追问那一轮。四个动作步数：锁屏通知 → 读结果 1 步、知道了 1 步、再来一次 1 步、有用 1 步、说一句 0 步。

### M1 · 3–4 周

每日简报卡（服务端从 GET /tasks 拼，8:00 一张，说「今日」随叫）；「进度」只答不推；关键词清单（今日 / 任务 / 进行中 / 交付物 / 例行 / 找 X / 序号）；例行条目卡（跑一次 / 暂停·恢复 / 删除二次确认）；message_id ↔ task / deliverable / routine 映射表；幂等（同一 message_id 的「再来一次」只接受一次）与离线补投（长连接恢复后拉最近 1 小时）；长文或含表交付物转飞书云文档发链接卡；PWA 打磨（表格、代码块、44px 行高、离线 / 401 态）；配对二维码吊销。

### M2 · 独立 App · 8–12 周 · 条件触发

服务端先行：配对 token 做成 dsh 层的官方 token API（ECOSYSTEM 形态矩阵缺项），不做 tasks 包里绕过 `rejectUntrusted` 的旁路；带 cursor 的事件日志 + seen/ack；SSE 事件流 + 推送中继（APNs / FCM）；`GET /feed?before=` 合并流；`GET /tasks` 分页 / since；文件交付物下载路由；领域包 data 渲染契约。客户端：S0 / S1 / S1a / S4 新写，S2 / S3 / S5 / S6 复用；拆 PWA 三 tab；深色模式；TestFlight 内测；Android APK。对外命名：M0–M1 叫「飞书里的 MyWork」，「App」留给 M2。

## 6. 依赖

### 认证
- dsh 浏览器认证（dsh-client-connection 0.1.6-alpha.2 README:37-41）：每进程随机 launch token，只在 `GET /` 用 `?token=` 换签名 cookie 后重定向；cookie HttpOnly、SameSite=Strict、绑定 host:port、默认 30 天；不接受 root 之外的 query token，不接受 Authorization 头；Host 必须是 loopback 或 trustedHosts；Origin 必须等于 Host；sec-fetch-site cross-site 拒；`--host 0.0.0.0` 不支持。
- 结论：原生 App 无法用 bearer token；Capacitor 自定义 scheme 的 Origin ≠ Host 会被 403；今天能上线的只有同源 PWA / WebView。
- 评审核对（未在本轮复核）：dsh-web-app `lib/startup.js` 只拒 `0.0.0.0`，`--host <局域网IP>` 加 `--trusted-host` 是现成 CLI 参数。二维码里的 authority 必须和手机以后访问的一模一样（cookie 绑 host:port）。
- 所有 mywork 路由的守卫是 `rejectUntrusted` → dsh `connection.requestRejection`（tasks/harness.js:76-91），由包自己按路由调用；M2 的 token 校验应做在 dsh 层而不是 tasks 包旁路，否则等于给电脑开后门，且 dsh 官方给了 token API 就得拆。
- trustedHosts 打开后，内网任何设备拿到 `?token=` 链接就有 30 天 cookie：二维码一次性、短时效，桌面端能吊销。

### 到达
- 服务只监听用户电脑 loopback（开发环境 `node dsh/lib/bin.js web --port 3090`）。手机要访问必须同一局域网或 Tailscale / frp，且写 trustedHosts。
- 合盖、关机、断网即失联，对 PWA、飞书机器人、独立 App 三者一样；App 解决不了。缓解：桌面壳常驻、设置里显示在线 / 离线；离线期间到期的例行本来就有「启动后补跑一次」（index.js:100-101）。
- 飞书路线绕开到达问题的原因：飞书事件订阅支持长连接模式（服务主动连飞书，不需要公网回调 URL）。

### 推送
- 现状：前端轮询（在跑 3s / 空闲 20s；client:33-34, 376-404），完成检测是两次 GET /tasks 快照差分；Notification 是浏览器本地 API；`mywork/task` 是进程内 `ctx.emit`（index.js:56-61），没有 SSE / WebSocket 暴露。
- 唯一能到手机的推送：packages/im 的飞书 bot 直推（feishu.js:39-49，`msg_type text`，发给 ownerOpenId，不需要先收到消息）。推送目标依赖 `notifyConfig.automation.default`，无 UI。推送正文默认 1500 字上限；微信路径经模型转发「偶尔轻微改动」。
- iOS Web Push 只对加到主屏且 16.4+ 的 PWA 开放，且要服务端推——M0 不做，M2 走 APNs / FCM，中继是一台不在用户电脑上的服务器，与「本机运行」有张力，需要单独决定。
- 开发环境 `.dsh-dev-home/home/dsh-im-connect/channels.json` 的 channels 为空（评审核对），飞书账号还没绑；M0 第一步是走 im-connect 的扫码绑定。

### 长连接
- dsh 的 `/api/remote.mux` WebSocket 承载 dsh RPC / $events，不承载 `mywork/task`。
- 评审核对（未在本轮复核）：`@michengai/dsh-im-connect@0.1.57`（`lib/channels/feishu.js:156-215`）已用 `sdk.WSClient` + `EventDispatcher` 接了 `im.message.receive_v1` 和 `card.action.trigger`，能发 interactive 卡与 file，带 QR 绑定和 owner 白名单；per-account agentPreset 在 `manager.js:209-210`。飞书同一应用只允许一条长连接，所以**不建第二条**；开发环境（:3090 / :3091）与正式环境同时跑会互踢，需要两个飞书应用或开关。
- im-connect 没有对外的入站钩子（`lib/index.js` 只有 inject，无 emit / provide），卡片按钮回调落在 im-connect 手里——所以 M0 的按钮动作走工具（mywork_rate / ack / say）而不是确定性路由器；M1 若要序号回复 + 卡片路由器，要先解决这一点。
- 企业自建应用要管理员开通 im:message 收发、卡片回调、长连接事件模式；个人用户可能卡在这一步。

### API 需要补的（业务层，不是壳层）
- 「变化」模型：带 cursor 的事件日志（完成 / 失败 / 核验有问题 / 例行有变化 / 提醒到点）+ 服务端 seen / ack，否则跨设备做不到「一次变化只打扰一次」。
- 消息身份：today/say 与 say 的 activity 带 id、请求幂等键、「已回复」信号；现在靠文本相等去重与整包重拉。
- `GET /tasks` 分页 / since / ETag：现在无过滤整包且被当作变化检测，蜂窝网络下每 3–20 秒拉全部任务扛不住。
- 推送目标与通知偏好的设置接口（目前在 im 包 `/notify`，默认目标无 UI）。
- 文件型交付物下载路由：交付物只有 markdown + data，任务写出的表格 / 幻灯片落在 `$DSH_HOME/mywork/workbench`，全仓库没有一条路由能下载。
- 领域包 homeWidget / renderer 是 dsh 客户端插槽，不是 API；独立 App 要在 data 上定义渲染契约。
- `GET /today` 只有当天线程，无分页；会话流上翻昨天需要 `GET /feed?before=`。
- 没有文件 / 图片 / 语音上传接口（POST ≤256KB JSON）。

### 壳 / 客户端
- tasks 客户端 `packages/tasks/lib/client.js` 是 dsh 的 C6 模块（要 `window.__ModuleLoader__`、平台 react、ctx.slots / locale / layout），脱壳要写一套小运行时；给 `MyworkSidebar.tsx` 加 <720 分支比独立 HTML 入口便宜。侧栏今天只有 compact 一种变体。
- tasks 客户端已有 720px 断点、表格横滚、safe-area 底部 dock（client:336-356）；未在 720px 以下真机检查过。
- iOS WebView 软键盘盖住底部 dock（用 visualViewport）；Android Chrome 行为不同。
- 微信：只能发给已发过消息的聊天，经模型一轮转发；平台政策收紧有先例（WhatsApp 2026-01 封杀第三方 AI）；只做降级版、不承诺可靠。飞书这条路实际覆盖的是已在用飞书的人。

## 7. 被反驳过的断言和修正

| 断言 | 结果 | 修正 |
|---|---|---|
| Cue 的主界面是 IM 式聊天；agent 是聊天成员；不是任务列表形态 | 部分成立 | 主界面是**会话列表**（手机：顶部一排 agent 头像 + 按时间排的会话行；桌面三栏），不是聊天本身。单聊无头像，只有群聊给每条 agent 消息加头像和名字。交付物两个入口：对话里的文件卡片 + 资料页「文件」列表；例行是资料页的「自动化」列表——MyWork 的例行列表、交付物列表在 Cue 里有对应物，不是 Cue 没有的层。与我们规则真正冲突的只有「回复是气泡而非正文」和群聊的多 agent 头像。手机端结论全部来自官方营销图，无第三方真机截图 |
| 现有 `/mywork-tasks/api` 足以支撑独立手机客户端，缺的只是认证、推送、长连接这类壳层能力 | 不成立 | 业务 API 覆盖核心闭环（清单、正文、评价、追问、建任务 / 例行、知道了 / 再来一次 / 取消 / 暂停）。但还缺：变化模型（事件日志 + seen/ack）、消息身份与幂等、分页 / since、通知偏好接口、文件交付物下载、领域包渲染契约；「原始对话」走 dsh 会话 RPC 没有 API 路径。认证 / 推送 / 可达是服务端基础设施，不是客户端壳层 |
| 办公类 agent 用户在手机上最常做的是看结果、追问交办、拍板；很少管理列表或看执行过程 | 不成立 | 没有任何按设备划分的行为数据；能核实的只有厂商定位（Cowork「遥控器」、Kimi「布置任务、跟进结果」、OpenAI 语音派活）。2026 年的趋势是把列表管理搬上手机（ChatGPT Scheduled 页 web + mobile、Grok Tasks 可暂停恢复），看过程被做成卖点或安全机制（Manus Remote Control、Cue 会话内进电脑、豆包灵动岛进度 + 接管）；Cue「长时间无进度」被评测列为缺陷。主动简报有边际递减（Pulse 下线并入定时任务、Slack bot 三周沉寂）。手机上四件事做到一跳可达，列表和过程保留为轻量形态，不砍 |
| 把网页三个页面原样搬到手机违反「一屏一件事」，且比聊天形态多一层导航 | 不成立 | FLOW.md:14「同一套页面，单列」、MYWORK-V2.md「任何宽度都是单列」本来就是手机形态；「一屏一件事」的粒度是页面职责，今日这一屏的「一件事」就是「问候 + 清单 + 例行 + 对话 + 输入框」。导航层数上原样搬到今日清单 / 任务列表 / 例行条目是 0 / 1 / 2 步，Cue 骨架是 1 / 2 / 2–3 步——多出导航层的是聊天形态。原样搬的真实代价只有一处：375px 上对话落到首屏之下，是排序 / 折叠问题，不是规则违反 |
| 方案三：M1 要在 packages/im 自建飞书长连接、自己收 card.action.trigger | 不成立（评审核对） | dsh-im-connect@0.1.57 已经占着这条长连接；飞书同一应用只允许一条。照做会与 IM 助理互踢或要求用户建第二个飞书应用。改为借 im-connect 的 per-account agentPreset + 补三个小工具 + 镜像到今日线程，一周可通 |
| 方案一：用 Capacitor 包现有 JS 客户端，四个条目页直接复用 | 不成立（评审核对） | Capacitor 自定义 scheme 的 Origin ≠ Host 被 dsh 403；tasks 客户端是依赖 `window.__ModuleLoader__` 的 C6 模块，不带 dsh 壳的 bundle 要重打运行时。复用成立的前提是同源（PWA / `server.url` 指向局域网同源地址） |
| 方案一：POST /pair + X-MyWork-Token 头在 rejectUntrusted 之前校验 | 有风险 | 等于绕过 dsh 信任层自建认证，要自己做限流 / 轮换 / 撤销；dsh 官方 token API 一出就得拆。放到 M2 并做在 dsh 层 |
| 方案一：成员 = 领域包 = 一个会话，会话列表当首页 | 不成立 | 只有 MyWork 时首页空壳；装四个包时首页就是 v2 刚删掉的场景选择器（ECOSYSTEM.md §1「领域包是生态单元不是界面选项」）。单成员不做列表；领域包展示面放在 MyWork 页 |
| 方案二：独立 HTML 入口 `/mywork-tasks/m` 只挂 tasks 客户端，3 天 | 偏乐观（评审核对） | 同上 C6 模块问题；给 MyworkSidebar 加 <720 分支更便宜 |
| 方案二 / 三：M1 验收「飞书收到完成」在今天的仓库能跑 | 不成立（评审核对） | 开发环境 channels.json 为空，飞书账号未绑；先走 im-connect 扫码绑定 |
| 「知道了」「再来一次」按「列表不放操作」挪到条目页 | 有代价 | 从网页行内 1 步变 3 步，恰是手机最高频的两个动作；见 §2 规则张力，需要拍板 |
| Cue 的 Agent 身份（电话 / 钱包）是该抄的方向 | 不成立 | 上线两天、邀请制、用户反馈几乎为零（Google Play 4.6 分 / 423 评，有登录卡死和崩溃）；Gartner 建议按「不可信自动化 + 审批闸门」对待；仅 3% 交易涉及 agent、23% 消费者信任 AI 付款、93% 商户认为 AI 方应担风险 |
| Cue 手机端没有底部 tab | 未验证 | 只有官方营销图（Play 5 张 + 发布推文图），无第三方真机截图，iOS 仍在审核 |
