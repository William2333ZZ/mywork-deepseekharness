# 评审：可行性

## 小结

从可行性看，三套共用的核心改动大多照现有模式就能做：预检脚本、代码判定「没有变化」、不挡活的「需要你」、deliver 加 path 和版本、规矩先进草稿、IM 默认目标。代码位置三套都基本准确。

差别在于对引擎结构改动的估计：
- 甲把「例行和计划段开短会话」标成中，丙把「每卷一个会话、每位同事同时跑 1 主加 1 卷」标成中，实际都是大。「一位同事对应一条会话、一次只跑一轮」贯穿 onSessionEvent、caller、pump、say、stop、recover（engine.js:42、383-395、481-494、646-652；store.js:146-149）。乙如实标了大。
- 三套都没说清网页出处快照从哪来：运行记录不存工具返回，可行的路是 dsh-tools 的 post-execute 钩子，待验证。
- 三套都把「approval 不再过期」当小改动，漏了 say() 会把下一句话当成回答。
- 三套都让同事拿用户的 key 跑对照评测。
- 三套的「打开原文」在同事空闲时都看不见。

借用上：
- 甲最守约束，只移植成 Node，Zotero 写明未验证。
- 乙和丙把 zotero-mcp、refchecker、pdf2zh 这些 Python 项目当命令行借，在 Windows 上起不来。
- 丙的 zotero-arxiv-daily「十来行」忽略了嵌入向量这个依赖。
- 三套都没装 dsh-aris 和 PerryLink 整包，这一点对。
- 有两点比预想好：dsh 0.1.6-alpha.2 里 llm-pi-ai（可接第二家模型，休眠挂载）、dsh-token-meter（用量统计）、dsh-goal 加轮次驱动（多轮续跑）都在 dsh-base 组合里，第二方挑错、费用显示、计划续跑都有现成的底座，但都还没在 MyWork 里实测。

结论：以乙为底。两周内能交节奏修复的第一版：预检、结构化时间、「需要你」、今天卡、规矩草稿、成稿文件化。3 到 6 周做核对：快照、字面核对、核对栏、第二方。独立会话、计划执行器和丙的「卷」放到 6 周以后，卷要等用户验证。再从甲移植成稿走文件、Node 版 Zotero、用 choice 做样本卡，从丙移植「只喂摘录」的二审和每月规矩体检。

## 建议的底

以方案乙为底，理由有四条。  1. 改动顺序和风险排序一致：A 阶段全是小到中，正好修真实断点（「没有变化」把东西藏掉、例行进不了「需要你」、晨报说没依据的话）；两个大项（例行独立会话、计划执行器）如实标大，还给了降级做法。 2. 不和现有约束打架：预检没变化不建运行，不吃全体 2000 条运行上限；今天卡由代码拼，零模型费用。 3. 「先查 dsh 自带的 goal、workflow」这个保留有实据：dsh-goal 和 dsh-goal-round-driver 都在 dsh-base 组合里（cordis.patch.yml:299-306），目标能跨重启保存、按轮自动续。如果能接上，计划执行可以从大降到中。 4. 不新增「卷」这种结构层。  乙需要修的地方：Python 依赖、approval 永不过期后 say() 吞消息、网页快照的来源、评测时 key 的保管，详见各项。  现实的先后顺序（按一位熟悉代码的工程师估）：  两周内能交的第一版： 1. approval/takeover 不自动续，同时修 say()（约 0.5 天）。 2. runRoutine 加预检分支：Node 脚本比快照哈希，没变化不建运行、不叫模型；第一次运行一定显示；安静轮交的文件仍进文件页（2–3 天，含一个模板脚本，巨潮公告列表或 models.dev 对比二选一）。 3. 结构化时间：交易日（stock-sdk 拉日历缓存成文件）、每月、一周多天（约 1.5 天）。 4. 不挡活的「需要你」：新工具加 needs.json，按资源去重，挂进铃铛（约 2 天）。 5. 晨报换成代码拼的「今天」卡（约 1.5 天）。 6. mywork_remember 改成只写草稿，资料栏可确认、删、改（约 1.5 天）。 7. IM 默认目标的设置界面（约 0.5 天）。 8. deliver 加 path，成稿从文件读，加版本和取代字段（约 1.5 天）。 9. 手机端只同步今天卡和「需要你」卡。 10. 每轮用量显示：先验证插件能否拿到 token-meter 的 tokenUsage 投影，能拿到就加进来。  3 到 6 周： - 论断/事实，加 post-execute 钩子存快照，加 Node 字面核对和复算。 - 阅读视图的核对栏，带甲的「先看 ≤7 处」和抽检。 - 同一位同事内的纠正记录和负记录。 - 第二方：用 pi-ai 路由或一次补全调用，只喂说法和摘录。 - 材料上传加 liteparse（要验证 win32 预编译包能进交叉构建）。 - 搜索去掉 2000 字截断，覆盖表和底稿。 - 运行记录按同事归档。  6 周以后： - 例行独立会话（大）。 - 计划执行器（先试 dsh-goal 的轮次驱动）。 - 预算和撞线处理。 - 判断台账和程序判定的条件。 - 按同事配 MCP 和 skill（先验证）。 - 丙的「卷」，等用户验证以后再说。

## 方案甲　6 分

**保留**

- 成稿写进 成稿/，deliver 只带 path，交付前在 engine.deliver（engine.js:655-663，现成的拒收口子）检查带单位的数字有没有绑编号，并排除年份、日期、文件编号（ai-berkshire issue 79 的教训）。大小是小到中，还省掉把 2 万字塞进工具参数的输出 token，deliverables.json 也不用每次整文件重写大正文（store.js:100-108）。
- 借用最守约束：不装 PerryLink 插件，也不装 dsh-aris 整包，只把规则和脚本移植成 Node；Zotero 写明「Node 读本地接口，未验证」。这和 BRIEF §1（Windows 没有 Python）以及 understand-ai-projects 里 dsh-aris 那条 d 款（写死 python3，启动失败会让整个 profile 起不来）一致。
- B9 把「approval/takeover 不再自动续跑」定位到 engine.js:826-840，位置对，是小改动（另需补 say() 一处，见问题）。
- mywork_flag 按站点合并，用户点「我登好了」后只重取受影响的来源。所有同事共用一个 Chrome 和它的登录态（kernel constraints 17），所以登录一次能解开所有同事，方向对，而且不需要新看板。
- 状态词表把机器的词和人的词分开：没查到、打不开、没去查、核不了，「没查到」不写成「不存在」。纯文案，零成本，有 hallucinator 和 ARIS 的教训作依据。
- 内核改动表的代码位置几乎全对：DocCard 1035、ReadingView 1078、TableBody 1124、openLive 629、engine 617/655/674/826、store 54-57、index 600-618/636-662，可以直接照着拆工单。

**问题**

- [major] C2「例行和计划段开短会话」标成中、只指向 engine.js:245-268，实际是大。「一位同事对应一条会话」这个假设贯穿整个引擎，不只是 ensureSession。
  - 依据：engine.js:42 mateSessionId；399 行 turns 按 mateId 建；481-494 行 onSessionEvent 用前缀切出 mateId；646-652 行 caller() 走 mates.bySession，而 store.js:146-149 只认 'mywork-mate-<id>'，所以短会话里调 deliver 或 mywork_* 都会报「不属于任何同事」；383-395 行 pump 每位同事同一时间只跑一轮；873-899 行 recover 只唤醒主会话；cancelSession、withdraw、stop 也都只认主会话。
  - 改法：按大排期。第一步只让「预检后有变化的例行」进新会话：会话 id 用 'mywork-mate-<id>~r<n>'，改 bySession、onSessionEvent、caller 的解析，并保持每位同事同一时间只跑一轮，跑完 dispose。计划段等这一步稳定后再接。
- [major] 网页出处快照没有来源。A1 的 mywork_source 要么让引擎重新抓（拿不到后台 Chrome 的登录态，动态页面也会和同事当时看到的不一样），要么让模型把原文塞进参数（贵，而且模型可能改写）。方案没有说用哪种。
  - 依据：运行记录不保存工具返回，argsPreview 和 resultPreview 都截到 240 字（engine.js:80-104，store.js:65，kernel constraints 3）；登录态在 $DSH_HOME/mywork/chrome-profile（kernel extensionPoints 6）。
  - 改法：用 dsh-tools 的 tools/post-execute 钩子，在同事会话里截下网页和浏览器类工具的返回，按哈希写进 出处/。这个钩子在 understand-ai-projects 的 dsh-aris 条里静态核对过，0.1.6-alpha.2 里有，但要先验证插件能挂上。PDF 走 liteparse 本地解析。
- [major] A5 纠正传播被低估。它包括程序直接替换成稿里的数值、新增运行触发类型（纠正、计划），以及把改动传给所有引用这条事实的同事。
  - 依据：TRIGGERS 只有 user/routine/system，而且 create 会把未知值改掉（store.js:38、157）；thread.cjs、workRecord（index.js:284-318）、activity()（636-662）都按这三种分支写；成稿是一整段 Markdown，没有数字锚点（store.js:259-269），同一个数字可能在正文里出现多次。
  - 改法：第一版只在同一位同事内做：计算类事实由程序重算，受影响的句子标出来，由同事出新版本。跨同事传播和程序直接改正文都先不做。新触发类型先只加一种，并补齐 thread.cjs 和手机端的分支。
- [major] 「能机查的规则写进 检查.json」没有定义检查的格式，引擎里也没有规则执行器。场景 15.6 的「拦下 1 次」全靠它。
  - 依据：方案 5.1、5.2；engine.deliver（655-663）现在只存不查；把自然语言规则变成可执行检查没有任何现成代码。
  - 改法：定死 4 到 5 种检查模板：来源级别、asOf 不早于最近一期披露、单位、口径字段、命中负记录。模型只能选模板、填参数，选不上的一律标「靠它自觉」。
- [major] approval 和 takeover 不再过期以后，用户发给这位同事的下一句无关的话会被当成对那张卡的回答。
  - 依据：engine.say 727-728 行：只要有等着回答的运行，就调 answer()；answerText 159-167 行对 approval 会把任意文字原样当回答。现在 24 小时后会过期，这个问题被掩盖了。
  - 改法：say() 里遇到挂着的 approval 或 takeover 时另开一轮新运行，那张卡继续等回答；回答只走卡片按钮。
- [major] 「没有变化也留一行」如果用运行来实现，会吃掉全体共用的 2000 条运行上限，这些运行就是对话历史。
  - 依据：对话现在过滤掉安静运行（index.js:446-455，client/index.js:1473）；MAX_RUNS 2000 全体共用，超了丢最旧的（store.js:54、101）；技术经理模板每 6 小时盯一次。
  - 改法：预检没变化时不建运行，只写例行回执（routines.js:191-200，每条例行留 30 条）。对话里那行小字由客户端从回执聚合出来画。
- [major] 在用户自己的任务上跑对照，用的是「用你的 key 调候选模型的 Node 脚本」，由同事来跑，等于让同事拿到 key，和方案自己写的「同事不碰密钥」矛盾。
  - 依据：方案 8.4、15.4 第 7 步；同事有 bash，权限 workspace-write，审批策略 never（engine.js:232-233），能读到它运行环境里的任何东西。
  - 改法：宿主侧加一个评测路由：从凭据库取 key 来跑脚本，同事只提交任务集和判定方法、读结果表。
- [minor] A6 挑错要求「只给文件路径，让它自己读」，这需要一个带工具、能读同事文件夹的会话，标成小到中偏乐观。
  - 依据：核验会话的工作目录是 $DSH_HOME/mywork/workbench，权限预设 read-only（index.js:326，engine.js:617），最多跑 5 分钟（engine.js:36）。另一家模型要靠 dsh-base 里休眠挂着的 llm-pi-ai 路由（dsh-base/cordis.patch.yml:107-115），在 MyWork 里怎么配置没有验证。
  - 改法：改成把「说法加原文摘录」直接写进提示（丙的做法），不开工具会话；超时按条数放宽；先验证 pi-ai 路由能被 selection 选中。
- [minor] 「打开原文」打开以后用户在同事页里看不到。
  - 依据：同事页的电脑区只在有运行在跑时才显示实时画面（client/index.js:1607-1610）；openLive 只是让后台 Chrome 打开那个网址（629-636）。
  - 改法：电脑区加一个不依赖当前运行的「按需显示画面」。A7 改记小到中。
- [minor] 上岗卡是带多个输入框的表单卡，现在没有这种卡，标成小到中偏乐观。
  - 依据：AskCard 只有 text、choice、approval、takeover 四种（client/index.js:1363，store.js:46）；自我介绍那一轮不能提问（engine.js:675）。
  - 改法：记中。第一版只做「它管什么」一张卡，其余三张用模板默认值。
- [minor] 手机端被并成一行「中」，工作量被低估。
  - 依据：每加一种卡片，手机端要改 apps/mobile/src 的 api.ts、thread.ts、screens/Thread.tsx 三处（kernel cheapExtensions 1）；甲新增约 10 种卡。
  - 改法：手机第一版只做「今天先看」和核对小卡。
- [minor] A3 的四个检查器加起来接近大。
  - 依据：financial_rigor 和 report_audit 约 40 KB Python，移植时还要修四个已知问题（understand-finance-projects ai-berkshire 条 howToBorrow 第 6 款）；时点检查需要每家公司最近一期披露日期的数据源。
  - 改法：第一版只做字面核对和复算；时点检查和存在性检查放后面。

**场景里仍不够的**

- 15.2：对 xlsx 做字面核对、让同事用脚本读单元格，都需要 Node 读 xlsx 的库，材料里没有；界面也读不了 xlsx，就地可读的只有 csv、tsv、md、txt、json（index.js:505）。
- 15.2 和 15.7：分 6 段写、超时自动续上都靠 C1（大），两周内做不出来。
- 15.3：用 Kimi 判 140 处引用是否支持原句，方案没说由谁调用。事后核验会话最多 5 分钟不够；在计划步骤里调另一家模型需要宿主侧发起，这一块没有设计。
- 15.4 和 15.8：跑对照要用户的 key，由同事跑就有泄漏问题（见问题列表）。
- 15.1：三个月几千条事实放在 事实.jsonl，右栏「底账」表需要新的分页路由；现有读文件接口只读前 512 KB，也不认 jsonl（index.js:505-519）。
- 15.6：R5 依赖「每家公司最近一期披露」的数据，需要写巨潮定期报告列表脚本；方案承认取不到时会退化成靠自觉。
- 15.5：手机上的 4 屏决定都是新界面，不是现成能力。

## 方案乙　7 分

**保留**

- A 阶段的六项（预检脚本、mywork_change、mywork_need、今天卡、IM 默认目标、approval 不自动续）全是小到中，直接修 realUse #8–#10，是三套里最适合两周起步的顺序。
- 预检没有变化时不建运行、不进对话，只写例行回执（routines.js 的 markRun 和 ran）。这样不吃全体 2000 条运行上限（store.js:54），也不用动对话过滤逻辑（index.js:446-455）。
- 「今天」卡由代码拼，不叫模型，可以照 runRoutine 的提醒分支（index.js:604-611）合成一条运行。零模型费用，也不会再说素材里没有的话（realUse #11）。
- 如实把后台会话（#17）和计划执行（#18）标成大，并给了降级做法（在主会话里按步骤连续发轮）。「先查 dsh 自带的 goal、workflow、todo」这一条有依据：dsh-goal 和 dsh-goal-round-driver 都在 dsh-base 组合里（cordis.patch.yml:299-306），目标能跨重启保存、按轮自动续，有机会把 #18 降到中。
- mywork_need 按资源记录，下一次抓取成功就自动消失，挂进现有的 activity()（index.js:636-662）即可，不用新看板。
- 论断带期间字段，字面核对能顺手标「可能过期」；规矩里能机查的范围收得窄（期间、单位、来源时效、口径标签），可以真的执行。
- 代码位置准确：index.js 600-618、665、792-810、36，engine.js 546、655-663、826-840、227-235，store.js 54-57，client 1124、629-636。

**问题**

- [major] 把需要 Python 的项目当成「命令行」直接借：zotero-mcp 的命令行技能、refchecker 和 verify_papers.py、pdf2zh/BabelDOC。
  - 依据：zotero-mcp 要 Python 3.10+，verify_papers.py 是 Python，refchecker 是 Python 命令行、HTTP 服务或桌面包，pdf2zh 要 Python 3.11–3.12（都见 understand-ai-projects 各条 runtime）；BRIEF §1 说 Windows 上没有 bash，也不自带 Python。
  - 改法：verify_papers 移植成 Node（只是查 arXiv、CrossRef、Semantic Scholar 的 HTTP 请求）；Zotero 用 Node 读 Zotero 7 本地接口（甲的做法，未验证）；翻译用 pdf2zh 的 Windows 独立 exe，或者依赖可选的 Python 环境。
- [major] 同事自己浏览来的网页没有快照。字面核对需要「网页用抓取时存的快照」，但只有预检脚本读的来源才会存。
  - 依据：运行记录不保存工具返回（engine.js:80-104，store.js:65，kernel constraints 3）。
  - 改法：同甲：用 tools/post-execute 钩子截下同事会话里网页和浏览器工具的返回，按哈希存进 快照/；先验证钩子能挂上。
- [major] #6 让 approval 和 takeover 不再自动续跑以后，用户的下一句话会被当成对那张卡的回答。
  - 依据：engine.say 727-728 行、answerText 159-167 行。
  - 改法：say() 遇到挂着的 approval 或 takeover 时另开一轮新运行。
- [minor] 规矩改了以后怎么生效，描述和现有机制不符。方案说「主对话轮换到新一代会话，沿用改职责时已有的机制」，但现有机制并不换会话。
  - 依据：index.js:248-259 和 378-396：改职责时是 recompose，把同一个会话重新挂到新一代 preset 上，会话本身不换；AGENTS.md 会不会因此被重读没有验证（kernel unknowns 5）。
  - 改法：先验证 recompose 之后 agent-instructions 会不会重读 AGENTS.md；不会的话，等 #17 用新会话来解决。
- [minor] 判断表的重审条件是一句自由文字，预检脚本没法求值，而 #8 说「判断条件由预检脚本求值」。
  - 依据：第 2 节样例把「储能出货同比 < 20%（季报）」写在一个字段里。
  - 改法：判断表加结构化的列：指标、比较、阈值、取数来源、检验日。写不成结构的条件，由模型在有变化时判断。
- [minor] 自测用 promptfoo、由同事拿用户的 key 去跑。promptfoo 不在材料里，依赖很重，Windows 上的表现没核实；key 也会暴露给同事。
  - 依据：方案 8.3 自己标了推断；同事有 bash，审批策略 never（engine.js:232-233）。
  - 改法：宿主侧写一个约 100 行的 Node 评测脚本，从凭据库取 key 来跑。

## 三套都漏掉的

- 网页出处快照从哪来：运行记录不保存工具返回（engine.js:80-104，kernel constraints 3），三套都假设有快照。可行的路是 dsh-tools 的 tools/post-execute 钩子（understand-ai-projects 的 dsh-aris 条静态核对过存在），但要先验证插件能挂上。
- approval/takeover 不再过期以后，engine.say（727-728）会把用户的下一句话当成回答，三套都只写了「改 826-840 行」，都标成小。
- 「打开原文」打开后看不见：同事页电脑区只在有运行在跑时才显示实时画面（client/index.js:1607-1610），而三套的核对都依赖在实时浏览器里看原文。
- 宿主侧的评测和第二模型调用器，以及 key 存在哪：三套的「在自己的任务上测」都让同事拿用户的 key 跑脚本；同事有 bash，审批策略 never（engine.js:232-233）。
- 预检脚本的网络问题：东财系接口挂代理会失败，要直连（stock-sdk issue #66、#42）；models.dev、OpenRouter、deprecations.info 在大陆不挂代理可能连不上（EDITIONS 10-1）。三套都没设计按域名分流，也没设计页面改版后怎么发现脚本坏了（解析失败要和「没变化」分开显示），热修通道还不存在。
- 全局并发上限 2（index.js:36）加上共用一个 Chrome 时，预检后叫模型的例行、计划段、用户的话谁优先，只有甲写了「插话优先」；两位同事同时用浏览器会抢同一批标签页。
- 数据迁移：deliverables.json 里的正文要搬成文件，旧的「它记住的」要并进规矩分节，三套都没给迁移步骤。
- Windows 实机：liteparse 的 win32 预编译包要进 macOS 上的交叉构建（项目记忆：用 npm --os/--cpu 加 pnpm supportedArchitectures 构建 win-x64）；所有 Node 脚本都没在 Windows 上跑过。
- 主会话本身仍会无限增长：三套都只把例行和计划拆出去，用户直接聊天多的同事照样会涨到 20 万 token；compaction-basic 会不会触发没验证（kernel unknowns 4）。只有丙给卷会话设计了换代。
- 新工具（批量 mywork_fact、mywork_change、mywork_need）每调用一次都会经 store.activity 整文件重写 tasks.json（store.js:100-108、182-193；82 轮时已经 680 KB），高频写入下的性能三套都没估。
- 截图、图片输入依赖视觉模型（乙场景 8、丙场景 1），默认的 deepseek-flash 能不能读图，三套都没核实。
- 桌面壳关窗口就退出（apps/desktop/main.js:180），例行就不跑了。三套都只把托盘常驻当前提，没有排进先后顺序。
