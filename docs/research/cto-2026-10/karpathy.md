# Karpathy 的做法：随手记、部分自主、上下文工程、LLM 会审、LLM Wiki 的团队用法（七个来源，2026-10-06）

注：karpathy.bearblog.dev 直接访问被 Cloudflare 拦下，两篇博客改从 Wayback 快照读取。X 帖子通过 fxtwitter API 读取原文。两段 YouTube 都抓了自动字幕（YC 演讲另对照了 Karpathy 自己在年终回顾里链接的现场听众转录稿）。下面写的都有原文出处，标【推论】的是我推出来的。

**1. The append-and-review note**
- 日期：2025-03-19
- URL：karpathy.bearblog.dev/the-append-and-review-note/
- 怎么做：Apple Notes 里只留一条名为 notes 的纯文本笔记，不建文件夹。
  - 追加：电脑或手机上，有任何想法或待办就加到最顶部。不加日期、链接或标签，只有 watch:/listen:/read: 这几个前缀方便 Ctrl+F。
  - 回顾：没有固定频率，隔一阵往下滚动浏览。值得留在注意力里的，复制粘贴回顶部；相关条目会合并、分组或改写；很少删除，不重要的自然往下沉。
  - 用例：早上写当天的小 TODO、记常用命令、记超参实验的命令和结果、脑子太乱时一次倒出来。
- 人和模型：全文没有提到 LLM，全部由人完成。核对就是回顾时的反复审视，经不起审视的条目自然下沉。
- 限制：只说多笔记、多文件夹带来认知负担，没有讨论失败方式。
- 【推论】CTO 同事：CTO 文件夹里放一个 notes.md，CTO 和同事都往顶部追加，同事不替他加结构。定时回顾时，同事只提议哪些条目上浮或合并，由 CTO 确认，默认不删。原法里"什么值得留意"由人判断，交给模型就有替人决定注意力的风险。

**2. Software Is Changing (Again)（YC AI Startup School）**
- 日期：2025-06-17 演讲，6 月 19 日视频上线
- URL：youtube.com/watch?v=LCEmiRjPEtQ；他自己写的章节摘要：x.com/karpathy/status/1935518272667217925
- 怎么做：他说部分自主应用有四个特征：替人管理上下文；编排多次模型调用；有专用 GUI 便于人审计；有自主度滑杆。
  - 滑杆的例子：Cursor 从 Tab 补全，到 Cmd+K 改选中的一块，到 Cmd+L 改整个文件，再到 Cmd+I 放手改整个仓库。Perplexity 从快速搜索到深度研究（10 分钟后回来看）。按任务复杂度调档。
  - 他自己写代码时怕大 diff，只做小步增量，一次一件具体的事，让循环转得很快。
  - 提示要写具体，提高一次验证通过的概率。
  - 教育场景拆成两个应用：教师端生成课程，学生端使用课程。课程是可审计的中间产物，AI 被限定在大纲之内。
- 人和模型：模型生成，人验证，目标是让这个循环尽量快。两个办法：
  - 加快验证：看红绿 diff，按键接受或拒绝。他认为读文字费力，看图是通往大脑的高速路。
  - 他原话是 "keep the AI on the leash"：一万行的 diff 对他没用，人仍是瓶颈，必须确认没有 bug、没有安全问题。
- 限制：
  - 模型会幻觉，能力参差（锯齿状）。
  - 有顺行性遗忘：不会像新同事那样随时间积累组织知识，上下文窗口要人直接去"编程"。
  - 容易被提示注入，可能泄露数据；agent 会过度活跃。
  - 演示到产品有很大鸿沟：2013 年 Waymo 试驾零干预，12 年后仍靠远程操作。他说这是"agent 的十年"，不是"agent 之年"。
  - 现阶段应多造 Iron Man 战衣，少造机器人，但要随时间把滑杆往右推。
- 【推论】CTO 同事：每个任务显示当前自主度档位，CTO 可以按任务类型调。交付物做成能快速核对的形状：小 diff，或"会议原文 ↔ 结论"对照，而不是长文。指令模糊时先问 CTO。执行前先交一份可审计的计划。

**3. Context engineering 推文**
- 日期：2025-06-25（转引 Tobi Lütke 6-19 的帖子）
- URL：x.com/karpathy/status/1937902205765607626
- 怎么做：他主张用"上下文工程"取代"提示工程"，定义是为下一步恰好填入对的信息。
  - "科学"的部分包括：任务描述与解释、少样本示例、RAG、相关（可能多模态）数据、工具、状态与历史、压缩。
  - "艺术"的部分是对 LLM 心理的直觉。
  - 应用层还要：把问题拆成控制流、打包上下文、按能力派给合适的模型、处理生成-验证的界面流程、护栏、安全、评测、并行、预取。
- 人和模型：帖子没有讲具体分工，只把生成-验证的界面流程列为应用层的责任。
- 失败方式：信息太少或格式不对，表现变差；太多或不相关，成本上升、表现下降。他认为"ChatGPT 套壳"这个说法是错的。
- 【推论】CTO 同事：每一步执行前组装上下文包：任务说明、CTO 认可过的样例、检索到的相关纪要片段、可用工具、压缩过的历史。不要把所有纪要都塞进去。分拣用便宜模型，判断用强模型。

**4. llm-council**
- 日期：仓库建于 2025-11-22
- URL：github.com/karpathy/llm-council；推文 x.com/karpathy/status/1992381094667411768
- 怎么做：一个本地 web 应用，界面像 ChatGPT，通过 OpenRouter 调多家模型，对话存成 JSON 文件。
  - 阶段 1：问题分别发给各模型（GPT-5.1、Gemini 3 Pro、Claude Sonnet 4.5、Grok 4），回答以标签页并排，供人逐个查看。
  - 阶段 2：每个模型看其他模型的匿名回答，按准确性和洞察排名。匿名是为了防止偏袒。
  - 阶段 3：主席模型拿到全部回答和评审，汇总成最终答案。
- 来由：他和 LLM 一起读书，习惯是第一遍自己读，第二遍让模型解释或总结，第三遍问答（2025-11-18 推文）。2025 年 2 月他就设想过让多个模型各自作答、再辩论、最后由主席定稿。在 How I Use LLMs 里他也说自己同时付费多家，把同一个问题问遍。
- 限制：
  - 模型常常愿意选别人的答案为最佳。读书时它们一致把 GPT-5.1 排第一、Claude 排最后，但他并不完全认同：他觉得 GPT-5.1 啰嗦，Claude 太简短。所以模型互评不等于人的判断。
  - 这个项目 99% 是 vibe coded，他明说不维护。他说集成方式还没被充分探索。
- 【推论】CTO 同事：只在高风险判断上启用会审，比如技术选型、事故根因。保留每个独立答案和互评给 CTO 翻看，并把分歧点高亮。明确告诉 CTO，排名不代表正确。

**5. 2025 LLM Year in Review（只取人如何与 agent 协作的部分）**
- 日期：2025-12-19
- URL：karpathy.bearblog.dev/year-in-review-2025/
- 怎么做：
  - 他认为 Claude Code 是第一个令人信服的 agent：循环地串起工具使用和推理，做长时间的问题求解。关键在于它跑在你的电脑上，用你已经装好的环境、数据、密钥、配置，交互延迟低，像住在电脑里的小幽灵。
  - 他认为 OpenAI 早期把 agent 放进云端容器是搞错了先后顺序。
  - LLM 应用层要做上下文工程、把多次调用编排成 DAG、给人在环提供专用 GUI、提供自主度滑杆，并通过私有数据、传感器、执行器和反馈回路，把"大学生"式的通才组织成垂直领域的职业者。
  - 他会为找一个 bug 写一个用完即弃的应用。
  - 人不爱读文字，模型应该用图、信息图、幻灯、网页来回应。
- 人如何核对：文中没有细讲。
- 限制：能力锯齿化，模型同时是天才和容易犯糊涂的小学生，可能被越狱骗去外泄数据。他也说自己对基准测试失去了信任。
- 【推论】CTO 同事：直接住在 CTO 的文件夹里，复用已有的仓库、登录和配置。结果用图表或小网页呈现。临时问题写一次性小工具。会议纪要和文档里的外来文本要按提示注入来防。

**6. How I Use LLMs（YouTube）**
- 日期：2025-02-27
- URL：youtube.com/watch?v=EWvNQjAaOHw
- 说明：他没有另写文字版，只有一条发布推文的章节表，以下来自视频字幕。
- 个人习惯：
  - 换话题就开新对话：token 会分散模型注意力，也更贵。
  - 留意自己用的是哪个模型、哪个付费档；他付 $200 的 Pro，同时付费多家。
  - 先用非思考模型，答得不好再换思考模型。
  - 新近或小众的信息，出于习惯去 Perplexity 搜。
  - 深度研究用过 10–20 次，结果只当初稿，再去读引用。
  - 读论文或书时先要摘要，再边读边问，"不要独自读书"；还会让 Claude 画章节概念图。
  - 写代码不用网页聊天，而是用 Cursor 的 Composer；不行就回退手写。
  - 约一半查询用语音，手机上约 80%；Mac 上用 SuperWhisper，绑 F5 键。
  - 用自定义指令（例如让它别像 HR 那样说话）。
  - 自建 custom GPT，指令里总放少样本示例，用 XML 式标签分隔。
- 人如何核对：
  - 回到原始来源核对，比如药盒上的成分。
  - 图片里的数值先让模型转成文字，确认读对了再分析。
  - 数据分析生成的代码他总是读。他抓到过模型偷偷把 2015 年估值填成 0.1，还把约 20 万亿的外推值报成 1.7 万亿。
- 限制：
  - 幻觉；深度研究做的表格漏了 xAI。
  - 不同应用的工具不一致，没有工具时模型会硬算出错。
  - 模型像"心不在焉的初级分析师"；看不懂代码的人，他不太推荐用这类工具。
- 【推论】CTO 同事：数字结论附上可运行的计算代码供 CTO 抽查。研究结果标为初稿，并列出待核对的引用。重复性任务固化成带样例的模板。

**7. LLM Wiki gist（只取团队用例和人在环部分）**
- 日期：2026-04-04（前一天发过推文 x.com/karpathy/status/2039805659525644595）
- URL：gist.github.com/karpathy/442a6bf555914893e9891c11519de94f
- 团队用例：原文只有一句。内容是：由 LLM 维护的内部 wiki，喂入 Slack 线程、会议转录、项目文档和客户通话；"可能"有人在环审阅更新；因为维护由 LLM 承担，wiki 能保持最新。谁来审、多久审一次、权限怎么定，原文都没有写。
- 人在环相关的做法：
  - 三层结构：原始资料不可改；wiki 完全归 LLM；schema 文件（如 CLAUDE.md）由人和 LLM 共同演化。
  - 摄入：他个人偏好一次只摄入一个来源并全程参与，读摘要、检查改动、告诉模型该强调什么。也可以批量摄入、少监督，由你自己决定并写进 schema。一个来源可能改动 10–15 页。
  - 好的答案会归档回 wiki。
  - 定期做体检：查矛盾、过时内容、孤儿页、缺页。
  - index.md 每次摄入都更新；log.md 只追加，用统一前缀，可以 grep。
  - 他在 Obsidian 里实时看结果，wiki 本身是一个 git 仓库。
  - 人负责挑来源、提问、思考意义，几乎不亲手写 wiki。
- 限制：规模变大后需要搜索工具；带图片的页面要分步读；他说这份文档是故意写得抽象的。
- 【推论】CTO 同事：用 raw/（纪要，只读）、wiki/（同事写）、schema 三层。每份纪要进来就更新相关页面并在 log.md 记一条。审阅可以逐条（Karpathy 本人的方式），也可以批量。体检中发现的矛盾，比如两次会议对同一个决定说法不一，作为问题去问 CTO。用 git 做撤销。团队场景下的审阅机制原文空白，需要我们自己设计。
