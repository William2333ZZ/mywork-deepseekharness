# 工程体检的规矩

照 Will Larson（度量、运营机制、用 agent 跑例行检查）、Google DORA 2025、The Pragmatic Engineer 的公司案例。程序算数，模型解释，用户判断。

## 文件

- 指标.md：用户的「章程」（像 autoresearch 的 program.md）：每个数一节——定义、从哪拿、怎么算、目标或阈值、用户现在的判断。用户改它，你照它做。
- 脚本/：每个数据源一个脚本，拉数、算、把结果追加进 指标.tsv。
- 指标.tsv：制表符分隔，列：日期、指标、值、来源、备注。只往后加，旧行不改。
- 图/：每个指标一张趋势图（有目标线就画上）。
- 导出/：用户导出来丢给你的数据，只读。

## 每周

1. 跑 脚本/，把上周的数追加进 指标.tsv，更新 图/。
2. 和上月、上季、去年（有的话）、目标比。
3. 只报：越过阈值的、违背 指标.md 里用户判断的、连续三周往同一个方向走的。每条附：算出这个数的命令、图、一个可能的解释（标「推断」）。
4. 脚本跑失败、数拿不到、数据源变了：一定说出来。
5. 没有值得报的，就只回一句。

## 口径

- 吞吐（每周合并的 PR、部署次数）永远和不稳定（变更失败率、线上事故数和时长、回滚）一起报——DORA：AI 让吞吐上去的同时，不稳定也跟着上去。
- 只按团队看，不按个人排名，不拿来评绩效（Larson：用优化指标评绩效是常见失败）。
- 不用 AI 采纳率、代码行数这类指标；AI 用量只按使用程度切片对比，不设使用率目标（Pragmatic Engineer 里各公司的做法）。
- 一次只加一个新指标。

## 季报（用户要时）

照 Larson 的模板起草：摘要（2–4 句，留给用户写判断）、交付（约 3 项）、指标（约 3 张趋势图，当前值、趋势、目标）、编制与招聘、成本、附录。写起来痛苦的地方，说明数据源该改了。
